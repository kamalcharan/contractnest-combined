─── ROOT CAUSES FIXED ───────────────────────────────

A. TAG FILTER (and more): contactController.listContacts silently dropped
   `tags`, `user_status`, `show_duplicates`, `sort_by` and `sort_order`
   from req.query — the edge list route supported ALL of them all along.
   Chip counts came from /stats (which forwards tags) so they looked right
   while the list ignored every chip click. Sorting was equally a no-op.

B. GUEST DUPLICATION: NOT the contacts UI (both create paths already run
   checkDuplicates). gs_checkin_guest's reuse-lookup required an EXACT
   string phone match (stored '+919059951359' vs typed '9059951359') AND
   an existing Guest tag — so every repeat guest visit inserted a fresh
   contact. Proof: the Tejaswinni pair (8 Aug + 5 Sep), identical
   phone+email, created_by NULL at ~07:35 IST on meeting Saturdays.
   Migration 076 (LIVE): last-10-digits normalized match, no Guest-tag
   prerequisite, oldest match wins, stale 10-arg overload dropped.
   Verified: bare '9059951359' now resolves to the 8 Aug original.

    - SOURCE OF RECORD ONLY — all seven already applied live. Do not re-run.
    - 082 (2026-09-16 late, owner live-tested: created "mr cherry" with an
      identical phone to two existing contacts and got no warning, even
      after item 13's frontend property-name fix). Root cause was
      server-side, not frontend: check_contact_duplicates (the RPC the
      create-time check actually calls) threw "column tenant_id does not
      exist" on EVERY call — a dead COALESCE fallback referenced
      t_user_profiles.tenant_id, a column that table has never had.
      Postgres validates column references at PARSE time regardless of
      whether that branch would ever run, so the call failed even with a
      valid p_tenant_id passed explicitly. The error was swallowed by the
      RPC's own exception handler into {success:false}, which the caller
      silently treats as "no duplicates" — so phone/email duplicate
      detection at create time has been unconditionally broken this whole
      time, independent of item 13's property-name fix (both bugs had to
      be fixed together for the alert to actually appear). Removed the
      dead branch. Also dropped a stale 3-arg overload of the same
      function with NO tenant filtering at all (confirmed zero live
      callers) — a real cross-tenant leak risk, same "stale overload
      beside the current one" pattern as migration 076's guest dedupe fix.
      Verified live: re-ran the exact call that previously errored and it
      now correctly returns hasDuplicates:true with all three matching
      contacts.
    - 078 (2026-09-16 late, owner call: "RPC should be good option") fixes
      the root cause behind item 8 below: update_contact_idempotent_v2
      accepted p_contact_persons since it was written but its body never
      read it — every attempt to save linked/alternate contacts on an
      EXISTING contact (incl. the old ProfileDrawer) was a silent no-op;
      persons only ever persisted at contact CREATE time. Now handles it
      with the same full-replace convention the RPC already uses for
      channels/addresses: a person with an id is updated, one without an
      id becomes a new child contact (individual · team_member ·
      parent_contact_ids=[parent]), and any existing child left out of the
      array is unlinked (never deleted). Verified live in a self-contained
      rollback transaction (throwaway parent+child, create/edit/unlink all
      asserted, RAISE EXCEPTION at the end — zero rows persisted).
    - 079/080/081 (2026-09-16 late, owner: "merge duplicates — what is your
      proposal" → agreed to fix detection first, as its own increment
      ahead of a future merge action). Found the whole duplicates feature
      was silently non-functional: t_contacts.potential_duplicate (what
      the stats count AND the already-shipped "Possible duplicates"
      checkbox depend on) was 0/460 populated — the function meant to
      compute it, update_duplicate_flags(), is called from nowhere in the
      app or a cron. On top of that, list_contacts_with_channels_v2's
      p_show_duplicates parameter was ALSO dead (same "accepted, never
      read" bug as 078, just a different RPC) — the older RPC it replaced
      implemented it correctly, so this was a silent regression.
      079 adds get_tenant_duplicate_contact_ids(): computes duplicates
      LIVE at query time (mobile normalized to last-10-digits — same
      convention as 076, since an exact-string compare misses
      '+919059951359' vs '9059951359', the exact bug class behind the
      Tejaswinni duplicate — or email case-insensitive), scoped to one
      tenant + one environment, excluding archived AND child contacts
      (children are hidden from this population by 077 anyway). 080 wires
      the list RPC to it. 081 swaps get_contact_stats's duplicate count
      from the dead column to the same live set, so the stat and the
      filter always agree.
      Verified live: a real check against BBB found 4 pairs a naive exact-
      match would flag (e.g. two "CHARAN KAMAL" rows) — all traced to be a
      LIVE contact and its TEST-environment counterpart from BBB's pre-go-
      live setup, correctly excluded since detection is scoped per
      environment (merging across live/test would mix test data into
      production). A guarded rollback transaction then created two
      throwaway contacts with the same number in different formats and
      confirmed both were flagged, then rolled back with zero residue.
      Current true count: 0 real duplicates in BBB right now (Tejaswinni,
      the one known case, was already merged manually earlier this
      session) — the feature was simply blind before, not that nothing
