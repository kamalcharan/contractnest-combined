─── WHAT CHANGED ────────────────────────────────────
 ONE BOARD, TWO LANES. The reader is now jtd_ops_board (014): the same row
 model as the collections board plus every open service visit from
 t_contract_events (event_type='service', status scheduled/due/overdue/
 in_progress — the truth; the JTD mirror is incomplete: 299 open live visits
 have no n_jtd row, so the lane reads events directly). Each row carries
   lane        collections | services
   kind        visit_in_progress · visit_overdue · visit_today · visit_scheduled
   anchor      the visit's scheduled date → the same WHEN buckets
   owner_id    the technician (services) / the call assignee (collections)
   slot_state  confirmed (appointment accepted) · proposed (requested /
               rescheduled, awaiting the customer) · none
   visit {}    block, n/m, technician, slot {id,status,at,confirmed},
               open ticket {id,number,status}
 APPOINTMENT = the visit's agreed slot with the customer (t_appointments,
 one active per event). No separate lane; "Confirmed"/"Proposed" is the
 slot filter.
 FIVE TOOLS (each takes an actor, loads + locks the event, refuses with a
 machine-readable reason, mirrors to n_jtd + n_jtd_history when a job exists):
   jtd_assign_visit        technician on the event (+ open ticket)
   jtd_schedule_visit      slot (proposed or agreed) — retires a closed
                           appointment, create_appointment, update_appointment
                           accepted|rescheduled|requested; a proposed slot
                           also moves the event date so the card sits in the
                           right column; agreed = customer notified by the
                           existing appointment flow
   jtd_confirm_visit_slot  the customer agreed to the proposed slot
   jtd_start_visit         ticket in_progress (created with p_start_now if
                           none) + event in_progress
   jtd_complete_visit      ticket completed (created first if none), event
                           completed, appointment completed
   Refusals: actor_required · visit_not_found · visit_closed ·
   visit_in_progress · assignee_not_in_tenant · already_assigned ·
   scheduled_at_required · slot_in_past · no_slot_to_confirm ·
   already_confirmed · visit_already_started · downstream_refused (the
   wrapped RPC said no — its message is passed through).
 ONE CARD, STILL. JobCard renders visit rows with the same code:
   in progress            → Mark done · Assign
   overdue/today/scheduled→ Start visit · Schedule/Reschedule · (Confirm slot
                            when proposed) · Assign · Mark done
   primary = Confirm slot › Start visit › Schedule. Panels: Assign (team
   picker), Schedule (date-time + "Agreed with the customer"), Mark done
   (notes). Evidence line: Visit n/m · block · technician or "no technician"
   · slot state. History link opens the contract timeline (event-audit rows
   of service events now read "Service visit …", not "Billing event").
 PAGE: lane chips All · Collections · Services (counts ignore the lane
 filter); kind chips gain Visits overdue · Visits today · In progress ·
 Visits scheduled and hide the other lane's chips when a lane is picked;
 a Slot select (confirmed / proposed / none) on Services; channel + cycle
 selects hide on Services; Who now means call assignee OR technician.
 Headline gains "N visits overdue, N visits today, N visits in progress" in
 the needs-you clause and "3 visits, 2 payments and 1 reminder fall due …"
 forward (one verb — "falls" only when the whole subject is 1; fixes
 "1 payment fall due"). Under it, a signal line — never in the headline —
 "N visits have no technician yet →" (facets.who.unassigned_visits, which
 ignores the lane and kind filters) jumps to Services · Unassigned.
 "What happened" merges visit activity (visit_assigned · visit_scheduled ·
 visit_slot_confirmed · visit_started · visit_completed) with the payment
 feed, newest first.
