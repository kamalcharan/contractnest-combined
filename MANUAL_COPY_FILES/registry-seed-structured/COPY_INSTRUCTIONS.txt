OWNER PRINCIPLE ENCODED
───────────────────────
"Registry is by-select — the user selects what he owns, and seeding
should follow that same pattern." Nothing is invented: one row per
picked template, exactly as before. What changes is the SHAPE — seeds
now come out looking like rows the product's own manual add flow
produces (verified against real manually-created rows):

  BEFORE (live, e.g. tenant "setup"):       AFTER:
  flat list, no parents, every row           Main Site            (campus)
  good/medium, no location — the done        └─ Building A        (building)
  screen's "Campus→Building→Floor→Unit"         ├─ Parking Area   (zone)
  claim had nothing behind it                   ├─ HVAC System    — medium, located
                                                └─ DG Set         — HIGH, located

DETAILS
───────
• Hierarchy exactly like manual adds: specifications.entity_type
  ('campus'/'building'/'zone' — valid parents per entityTypeConfig.ts)
  linked via parent_asset_id. Facility picks ('asset' templates) become
  zone nodes; equipment attaches under Building A with a location.
• Criticality varies by equipment class (DG/transformer/lift/UPS/fire →
  high; parking/washroom/landscaping → low; else medium) instead of a
  wall of 'medium'. All seeded rows flagged specifications.is_sample.
• Skeleton (campus+building) created once per tenant, idempotent;
  template-row idempotency unchanged (same partial unique index).
• Optional p_site_name param for later ("{Business} — Main Site");
  the old 3-arg signature is DROPPED first — otherwise CREATE with the
  new arg would create an ambiguous OVERLOAD and break the API's rpc().
• is_live=false unchanged (test env, same philosophy as contacts).
• Part 2 of the migration BACKFILLS existing flat-seeded tenants
  (setup, ping, sign, final, …) into the same structure — only rows
  with seeded_from='onboarding' and no parent; manual rows untouched.
