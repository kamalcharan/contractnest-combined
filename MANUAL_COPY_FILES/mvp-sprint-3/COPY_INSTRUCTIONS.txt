1. /start/contract — the one real build
───────────────────────────────────────
  Client (the 3 seeded contacts + Add someone) · what's included (their own
  blocks, pre-ticked) · term · billing cycle · start date · running total.

  EVERY CALL ALREADY EXISTS. No template, no LLM, no new endpoint:

    vaniComposerService.shortlist(intent)
        returns the tenant's own blocks already carrying activity, cycle_days
        and price — the grouping m_cat_blocks does not store is resolved
        server-side here.

    vaniComposerService.assemble(intent, buyer, candidates, selection)
        STEP 5, deterministic. The LLM step (selectBlocks) is SKIPPED: the
        tenant ticks boxes, so the selection is built locally in the exact
        shape assemble() expects.

    useContractSubmission.submit(draft, 'client')
        the same path the wizard and the VaNi composer both finalize through.

  The wizard, the VaNi composer, bulk assign and template assignment are all
  UNTOUCHED. This is a narrow front door for someone four minutes old, not a
  replacement.

  CREATED IN TEST — AND IT HAS TO BE, NOT JUST OUGHT TO BE
  Checked against production before building this. Onboarding seeds:

    tenant             live contacts   test contacts
    feed / live / set         0               3
    sharma elevators          0               3

    tenant             live blocks     test blocks
    feed / live               42             41
    set                      110            109

  The sample contacts exist ONLY in test — which confirms your point that VaNi
  switches to test before creating a contract; the seeder does it server-side,
  which is why there is no client-side switch to find. Blocks are mirrored into
  both. So running this screen in LIVE would show an empty client dropdown and
  the screen would be unusable. Test is required, not preferred.

  It is a rehearsal against sample contacts and must not land in a real
  ledger. api.ts reads localStorage['is_live_environment'] on EVERY request
  (getCurrentEnvironment, api.ts:75) and the request interceptor overwrites
  any per-request header, so flipping that key is both necessary and
  sufficient. AuthContext is NOT modified.

  Acceptance is 'signoff', not 'auto': auto-accept would flip the contract
  straight to active and generate invoices and billing events for a rehearsal.

  Skippable. If the catalog is empty or shortlist fails, the screen says so and
  offers to move on rather than trapping the tenant.


2. /start/plan — a wrapper, nothing designed
────────────────────────────────────────────
  Renders the SAME PlanCard component /businessmodel/tenants/pricing-plans
  renders, from the same fakePricingPlans fixture.

  WHY THE EXISTING PAGE COULD NOT SIMPLY BE ROUTED IN — you asked whether an
  existing screen could just be shown. It cannot, for two reasons:

    a) all three of its actions navigate OUT of onboarding:
         line 71 -> /businessmodel/tenants/pricing-plans/{planId}/subscribe
         line 76 -> /businessmodel/tenants/pricing-plans/{planId}/trial
         line 81 -> /businessmodel/tenants/subscription

    b) TWO OF THOSE THREE ROUTES DO NOT EXIST. App.tsx registers only an
       `index` child under /businessmodel/tenants/pricing-plans, so "Subscribe"
       and "Start trial" land on NotFoundPage TODAY for any tenant who clicks
       them. Same class of bug as the lov-setup 404. Reported here, NOT fixed
       in this batch — see OPEN ITEMS.

  So the component is reused and the handlers are onboarding-appropriate.

  WHAT IT WRITES: completeVaniStep('done', { selected_plan_id }) into
  step_data only. t_bm_tenant_subscription is deliberately NOT written —
  PlanCard is fed from a JSON fixture, and a subscription row pointing at a
  fixture id would be worse than no row. When the 8 real plans in
  t_bm_pricing_plan are wired up, that is the one line to change, and the same
  row becomes the pre-MVP/MVP signal for revealAll.

  LEAVING ONBOARDING IS A HARD NAVIGATION (window.location.assign), on
  purpose: the contract screen put the session into test via localStorage, but
  AuthContext only reads that key when it initialises (AuthContext.tsx:169). A
  router push would leave the header badge saying "Live" while every request
  went to test. A full load re-seeds AuthContext so the badge tells the truth.
