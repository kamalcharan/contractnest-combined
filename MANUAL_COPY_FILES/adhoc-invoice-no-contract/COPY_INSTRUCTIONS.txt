WHAT THIS DOES
------------------
Adds a way to bill and settle a payment for a CONTACT who has no membership
contract at all — e.g. a Group Session guest fee (the gap flagged in
CLAUDE.md: "guest session payments have nowhere to post"). Per your spec:
  1. Select a contact (entry points: Group Sessions "Payments to confirm"
     panel per-row "Invoice" button, and the Contacts Financials tab's
     existing "Create Adhoc Service" card, previously wired to nothing)
  2. Opens a new invoice-creation dialog (there was no existing one to
     reuse — the old INV-10010-style page is read-only, no create logic)
  3. Pick items from Catalog Studio — reuses BlockLibraryMini +
     BlockCardSelectable, the SAME card component Contract Wizard uses
     (both "select" catalog cards and "FlyBy" quick-add cards for one-off
     items not in the catalog)
  4. Invoice + receipt are created together in ONE transaction, always
     fully paid at creation — no separate "record payment" step

  contractnest-edge/supabase/migrations/finance/001_adhoc_invoice_no_contract.sql

  - t_invoices.contract_id: NOT NULL -> nullable
  - t_invoices: + contact_id (uuid, FK t_contacts), + line_items (jsonb)
  - t_invoices: + CHECK (contract_id IS NOT NULL OR contact_id IS NOT NULL)
  - t_invoice_receipts.contract_id: NOT NULL -> nullable
  - NEW RPC: create_adhoc_invoice(p_payload jsonb) — creates the invoice
    (status='paid' immediately) + a settling receipt, same number-generation
    and receipt-insert pattern as the existing record_invoice_payment RPC,
    just with contract_id NULL throughout. Tested live end-to-end against a
    test-tenant contact (is_live=false) before touching anything real.
  - get_tenant_receivables: 2 of its 4 near-identical internal `inv` CTEs
    changed from INNER to LEFT JOIN t_contracts (the other 2 are scoped to
    open/unpaid invoices, which an always-paid adhoc invoice can never be —
    deliberately left untouched to keep the blast radius minimal on an
    already-complex function). Verified live: BBB's real 49-invoice
    collected_total (313500) and invoice_count (49) unchanged before/after;
    the test adhoc invoice's amount correctly appeared in collected_total
    and the invoice list with a new is_adhoc:true flag.
  - get_contact_cockpit_summary: STEP 7 (invoice list) and STEP 8 (payment
    pattern) now UNION in invoices where contract_id IS NULL AND
    contact_id = the contact — unreachable through the existing
    buyer_id/CNAK-accessor JOIN chain since there's no contract at all.
    STEP 6 (outstanding balance) untouched — same reasoning as above.
    Verified live against a real contract-linked contact (total_paid 248500
    unchanged) and the test adhoc-invoice contact (correctly appears).

  contractnest-edge/supabase/migrations/finance/002_adhoc_invoice_declaration_link.sql
  (also already applied live — see the "UPDATED after first round of live
  testing" note at the top of this file for why)

  - t_session_payment_declarations: + adhoc_invoice_id (uuid, FK t_invoices)
  - create_adhoc_invoice: now accepts an optional declaration_id; when
    present, validates it (pending, no existing invoice, belongs to this
    tenant/contact) BEFORE creating anything, then stamps adhoc_invoice_id
    in the SAME transaction as the invoice+receipt. Verified live: a second
    call with the same declaration_id cleanly fails with "Declaration not
    found, already processed, or already invoiced" — no duplicate invoice.
  - gs_pending_declarations: now returns adhoc_invoice_id +
    adhoc_invoice_number (LEFT JOIN t_invoices) so the panel can tell,
    per row, whether it's already been invoiced.

PRODUCTION CHECKLIST
---------------------
  Transaction Management : create_adhoc_invoice's invoice insert + receipt
                            insert are one PL/pgSQL function body — a single
                            Postgres transaction; any failure (bad contact,
                            zero total, sequence exhaustion) rolls back both.
  Race Condition Handling : Invoice/receipt numbers use the same
                            get_next_formatted_sequence + self-healing retry
                            loop (up to 1000 attempts) already proven by
                            record_invoice_payment and the contract-event
                            scanner — row-locked via t_sequence_counters.
                            When invoked with a declaration_id, a pre-check
                            (pending + no existing invoice) plus a re-check
                            on the UPDATE's row count (RAISE if 0 rows
                            matched) close the double-click/concurrent-
                            request window — verified live, a second call
                            with the same declaration_id cleanly fails
                            instead of creating a duplicate invoice.
  Error Handling          : RPC catches all exceptions, returns
                            {success:false, error, details, error_code}
                            (never raises past its own boundary). API
                            controller validates contact_id/line_items/
                            payment_method before calling the RPC, and
                            separately surfaces an RPC-reported business
                            failure (e.g. "Contact not found") as a 400, not
                            a 500. Frontend surfaces both via the existing
                            VaNiToast component.
  Toasts                  : useVaNiToast (existing component) — success
                            shows the invoice + receipt number, failure
                            shows the specific error.
  Loaders                 : Submit button shows a spinner + disables while
                            createAdhocInvoice.isPending, same pattern as
                            RecordPaymentDialog.
