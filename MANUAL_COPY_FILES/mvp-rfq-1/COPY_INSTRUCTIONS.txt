THE FOUR REAL BREAKS, AND WHAT THE MIGRATION DOES
─────────────────────────────────────────────────
  BREAK 1  Vendors have no address.
           mapper.ts sends vendor_id + vendor_name only. Every vendor row is
           created with vendor_email NULL, so nothing can be delivered.
           BuyerSelectionStep's multi-select only carries (ids, names), so the
           email is not even in wizard state.
           -> BEFORE INSERT/UPDATE trigger fills name/company/email from
              t_contacts + t_contact_channels. Note t_contacts has NO email
              column — email is a channel row. Fixed server-side so every
              future writer inherits it, and so the wizard needs no change.

  BREAK 2  Only ONE vendor can ever hold a grant. THE REAL BLOCKER.
           idx_contract_access_unique_grant is unique on
             (contract_id, accessor_role, COALESCE(accessor_tenant_id, 0-uuid))
           Every RFQ vendor is role 'vendor' with a NULL accessor_tenant_id, so
           vendor #2 collides with vendor #1.
           Worse: update_contract_status only creates the grant IF buyer_id IS
           NOT NULL, and an RFQ has no buyer_id. So today an RFQ mints a CNAK
           that literally nobody can use.
           -> accessor_contact_id added to the unique key (this only LOOSENS
              the constraint, so no valid row can be invalidated), plus a
              trigger that mints one grant per vendor on rfq -> sent, each with
              its own secret_code. Shared CNAK, per-vendor secret.

  BREAK 3  Nothing can write a quote, and a vendor has no route.
           A vendor is a contact, not a tenant — authenticated routes are shut.
           -> rfq_resolve_for_vendor(cnak, secret)  — anon
              rfq_submit_quote(cnak, secret, ...)   — anon
              Same public pattern as the check-in page.
              The vendor sees the RFQ and their OWN row only — never another
              vendor's quote, never the invitee list, and never the buyer's own
              prices (they are quoting, not matching a number).

  BREAK 4  Editing an RFQ destroys quotes.  ** FIX THIS BEFORE, NOT AFTER **
           update_contract_transaction STEP 6 does DELETE-ALL then re-insert
           with response_status 'pending'. Harmless today only because no quote
           has ever existed. The moment BREAK 3 lands, a buyer adding a sixth
           vendor silently wipes five quotes.
           -> Now non-destructive: a vendor who responded is never removed, a
              vendor still on the list keeps their quote, only pending vendors
              dropped from the list are deleted.


YOUR ANSWER ON QUOTING, AND HOW IT LANDED
─────────────────────────────────────────
  "usually single, however it is left to users"

  quoted_amount stays the headline and is the only thing a comparison sorts on.
  quote_breakdown (new jsonb) carries optional per-block detail. A vendor who
  prices the blocks and gives no headline gets the headline computed as the sum
  — so a mixed set of responses still compares on one axis.

  NO NEW TABLE. quoted_amount keeps its meaning for every response.


WHAT THE MIGRATION DELIBERATELY DOES NOT DO
───────────────────────────────────────────
  rfq_award marks the winner accepted, the rest declined, and moves the RFQ to
  'awarded'. It does NOT create a contract.

  Your model is "the vendor initiates the contract". If accepting a quote
  created the contract, the BUYER would have authored it. So the migration
  stops at 'awarded' and leaves 'converted_to_contract' — which already exists
  in the state machine — for whatever you decide that next act is. Two shapes:

    a) winning vendor issues a contract from the awarded RFQ
       (matches your model; needs a source_rfq_id link column)
    b) flip the RFQ row itself to record_type 'contract'
       (no new column; the RFQ stops existing as a record of what was compared)

  I did not pick. It is the only remaining design choice in the cycle.
