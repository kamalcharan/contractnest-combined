WHAT THIS SOLVES
─────────────────────────────────────────────────
Completes the two remaining TIME-DRIVEN Group Session WhatsApp triggers:

  group_session_looking_forward → 3 days out AND 1 day out, to every active
                                  roster member (49 for BBB = 98/occurrence)
  group_session_noshow_regret   → session end + 2h, to roster members with no
                                  'present' attendance row (~15/occurrence)

group_session_absentee_reminder is NOT built — owner decision, on hold. Its
n_jtd_source_types row from 008 stays seeded and inert: no template, no
trigger, nothing enqueues it. No action needed to keep it that way.

Unlike migration 053 (where the JTD insert rode the transaction of an RPC that
was already firing), these have no host transaction, so they need a scheduler.
That brought four things that did not exist before:

  1. An IST-aware runner  — same class of bug as 048; "today" is Asia/Kolkata,
                            never the database's UTC current_date.
  2. An idempotency guard — n_jtd had NO unique index beyond its primary key.
                            A cron without one re-sends every 15 minutes,
                            forever.
  3. gs_roster_members()  — roster enumeration was locked inside
                            gs_dash_roster; now shared, so the dashboard and
                            the notifications cannot disagree about who is on
                            the roster.
  4. gs_member_whatsapp_phone() — safe phone lookup (see below).

Files Changed:
  - contractnest-edge/supabase/migrations/bbb-foundation/
        054_group_session_scheduled_notifications.sql          [NEW — RUN, don't copy]

Until both are set:
  - looking_forward sends NOTHING (its approved template carries a start_time
    variable; a blank would ship an empty placeholder, so the enqueue is gated
    on startTime being present)
  - noshow_regret sends NOTHING (cannot compute session end without
    startTime + durationMinutes)

This is by design — silent-but-correct beats a message with a blank in it.
Set the two values and both switch on with no code change.

⚠️ THE GUARD THAT MATTERS MOST
═══════════════════════════════════════════════════
Section 4b carries `s.occurrence_date >= v_today - 1`.

Without it, the first cron run after deploy would look back across the whole
schedule and fire a no-show regret for every past occurrence — for BBB that is
8 past occurrences x ~15 absentees = ~120 WhatsApps to real members about
sessions that happened months ago. The guard limits scope to yesterday's and
today's occurrences only.

Verified: deploying today (3 Aug) enqueues ZERO messages. Last occurrence was
25 Jul (outside the guard); next is 8 Aug (has not ended yet).

Production Checklist:
  ✅ Transaction Management: the scheduler is one function = one transaction;
     both INSERT…SELECT statements commit or roll back together.
  ✅ Race Condition Handling: ux_n_jtd_group_session_reminder (partial unique
     index) + ON CONFLICT DO NOTHING. Overlapping cron runs, retries, or a
     manual invocation cannot double-send. reminder_key ('lf_3' / 'lf_1' /
     'regret') discriminates the two looking-forward sends for the same
     occurrence + member, which source_id alone cannot.
  ✅ Error Handling: phone helper returns NULL rather than guessing on an
     unrecognised digit count (member is skipped, not mis-delivered); both
     halves gated on a template mapping existing, so an unmapped tenant is
     silent instead of manufacturing failed rows + DLQ noise; cron
     re-registration wrapped in an exception-swallowing DO block so re-running
     the migration is safe.
  ✅ Toasts: N/A — backend/scheduler only, no UI surface.
  ✅ Loaders: N/A — backend/scheduler only.
