BATCH: checkin-upi-qr-flow (2026-09-16)
═══════════════════════════════════════════════════
Closes the "check-in UPI pay link fails on real GPay" item that has been
open since 2026-07-25. Root cause finally isolated live this session, with
real ₹1 payments — see ROOT CAUSE below. Supersedes the *mechanism* of the
earlier checkin-upi-merchant-qr batch; that batch's payload fix (org_id/mcc
in the link) was correct and is still required — it is what makes the QR
built here valid.

Submodules affected: contractnest-ui ONLY.
No API, edge, RPC or DB change. No new dependency (uses the in-repo
src/utils/qrcodegen.ts already used by the group-session QRCard).

─── ROOT CAUSE ──────────────────────────────────────

The payload was never the problem after the org_id/mcc fix. What GPay
refuses for BBB's merchant-registered VPA (9849502193@kbl, U S R Travels,
mc=4722) is the DELIVERY MECHANISM:

  upi:// INTENT handed to GPay by a browser/other app
      → GPay opens, shows the amount, then FAILS at payment
        ("Payments to this receiver are not allowed by UPI network")

  Identical string read by GPay's OWN SCANNER as a QR
      → pays.

Proved live, same phone, same account, same minute:
  - physical bank sticker scanned inside GPay      → ₹1 PAID
  - same sticker via a QR-reader app → link → GPay  → fails at payment
  - our exact generated payload (amount + our reference + org_id/mcc)
    rendered as a QR, scanned inside GPay          → ₹1 PAID
  - same payload as a tap link from the check-in page → fails

Personal VPAs behave differently: the intent path DOES work for
kamalcharan@okicici (GPay opened and accepted it; a separate GPay-side
₹1,000-per-transaction cap applied, which is the payer app's rule and
nothing our page causes). So the intent button stays for personal-VPA
tenants and is removed only where it is a guaranteed failure.

The check-in page does `window.location.href = 'upi://…'` — the blocked
path. No link we can build will ever work for a merchant VPA; a QR does.

─── WHAT CHANGES (SessionCheckinPage.tsx, renderPayBlock) ───

 When the tenant's payment config carries merchant fields (org_id AND mcc):
   - The "Open UPI app" intent button is NOT rendered.
   - In its place: a QR of the exact buildUpiPaymentIntent() output for
     this member's due (amount + our CN… reference + org_id/mcc), rendered
     as a PNG so it can be press-and-hold saved, with the amount and payee
     under it and 4 numbered steps:
       Save QR → UPI app → Scan QR → gallery icon → pick it → approve →
       note reference → come back and enter it.
     Plus the line "Or scan the printed chapter QR at the desk…".
   - "Save QR · Pay ₹X" button: Web Share API with the PNG file where
     supported (Android Chrome / iOS Safari share sheet → Save image), else
     an <a download target=_blank> fallback; failure surfaces a hint to
     press-and-hold the image. Never navigates the page away.
   - "I've paid — enter my UPI reference" button → the EXISTING reference
     entry + duplicate checks + declaration flow, unchanged. paymentAttempted
     is only set by this explicit tap (never by saving the QR), consistent
     with the 2026-08-06 fix that stopped fabricated declarations.
   - One payment reference per page load (useRef), so the QR does not
     change under the member on re-render.
 When there are NO merchant fields (personal VPA, e.g. BBB's test config):
   - Zero behaviour change. Same intent button, same come-back alert.
 Also: the "App link failed, or already paid?" disclosure reads
 "Could not scan, or already paid?" on the QR path. Copy-UPI-ID box,
 already-declared-today warning, paid gate, dup alerts: untouched.
