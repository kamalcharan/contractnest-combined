-------------------------------------------------------------------
WHY THIS EXISTED AS A GAP
-------------------------------------------------------------------
Every plan card but the current one showed a disabled "Switch"
button. That wasn't cosmetic - subscribe_tenant_to_plan hard-refused
a second subscription (ALREADY_SUBSCRIBED) because superseding an
existing plan contract was an unanswered product decision. Owner
decision, 2026-08-09, in two parts:
  1. Switch is IMMEDIATE - the old plan ends right now, the new one
     starts right now. No "at next renewal" deferral.
  2. The old plan's unused allowance (remaining contract/RFQ headroom)
     and any accrued notification credits are FORFEITED, not carried
     over - a switch resets usage and credits to 0 and applies the
     new plan's limits/grants fresh, same as a first-time subscribe.

-------------------------------------------------------------------
REUSE, NOT A PARALLEL PIPE
-------------------------------------------------------------------
No new RPC, no new edge route, no new UI mutation:
  - subscribe_tenant_to_plan (the SAME RPC that already handles first-
    time subscribe) now also handles switching. Requesting the exact
    plan you're already on is still refused (ALREADY_SUBSCRIBED) -
    that's a no-op, not a switch; only requesting a DIFFERENT plan
    while already on one triggers switch logic.
  - Ending the old plan contract goes through update_contract_status
    - the existing generic contract status-transition function every
      other cancellation in the system already uses - instead of a
      raw UPDATE. That's what gives the switch a real audit trail
      (a row in t_contract_history, the same JTD event a manual
      cancellation gets) for free, rather than a status flip nobody
      can trace later.
  - The new plan contract is raised through the EXACT SAME code path
    as a first-time subscribe (same create_contract_transaction call,
    same block-building loop) - the only two differences are: the old
    contract gets cancelled first, and usage/credits reset instead of
    being left alone.
  - The edge function (POST /cat-templates/subscribe) and the UI's
    useSubscribeToPlan mutation are UNCHANGED - both already just
    forward whatever the RPC returns. was_switch/previous_contract_id
    are new fields in that same response, not a new endpoint.

-------------------------------------------------------------------
t_contracts HAS NO 'superseded' STATUS - USED 'cancelled'
-------------------------------------------------------------------
chk_t_contracts_status only allows: draft, pending_review,
pending_acceptance, active, completed, cancelled, expired, sent,
quotes_received, awarded, converted_to_contract. 'cancelled' is the
closest existing fit for "this plan contract no longer applies." The
REAL reason is recorded in the t_contract_history note - "Superseded
by switch to plan: Quarterly" - not left to be guessed from the bare
status. Live-verified this note is exactly what lands in the audit
trail (see TESTED LIVE below).

STILL PENDING
-------------------------------------------------------------------
  1. UI not yet copied/tested in a real browser - see STEP 3 below.
  2. No proration - a switch mid-term is billed the new plan's FULL
     price, not a prorated difference. Matches "immediate + forfeit"
     the owner chose; revisit only if proration is later wanted.
  3. Switching AWAY FROM per_contract (wallet) billing_mode was not
     in scope here and is untouched - subscribe_tenant_to_plan's
     v_existing lookup only ever matches PLAN contracts (excludes
     metadata.source='topup_purchase'), so a per_contract tenant can
     still separately subscribe to a plan without this code path
     even noticing the wallet balance. Whether that SHOULD switch
     billing_mode away from 'per_contract' is a product question
     nobody has asked yet - flagging it, not answering it.
  4. Downgrading FROM a paid plan back to Free works mechanically
     (Free is just another template with is_public=true) but was not
     specifically exercised in testing beyond the Quarterly->Yearly
     leg - the code path is identical either direction, low risk, but
     worth a manual click-through once the UI is live.
