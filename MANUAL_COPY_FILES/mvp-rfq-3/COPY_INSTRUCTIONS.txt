PART A — RFQ HOME (the toggle)
──────────────────────────────
  You asked: "no way to see where my RFPs are — the hub only shows contracts."
  It was worse than hidden: the hub never passed record_type, so RFQs LEAKED
  into the Expense vendor-contract list with status 'sent', which the contract
  pills don't model.

  Now Expense mode has a "Contracts | Requests" toggle. Requests filters
  record_type=rfq with an RFQ pipeline (Draft · Sent · Quotes In · Awarded ·
  Converted); Contracts filters record_type=contract, which also stops the leak.
  Revenue mode is untouched (RFQ is an expense-side concept).

THE DATA THIS NEEDED  (your question — "how will you use existing code")
────────────────────────────────────────────────────────────────────────
  Audited get_contracts_list against production first:
    * The FLAT (List) build ALREADY returned vendors_count — the live function
      had drifted ahead of the repo, so vendor count needed NO new work.
    * start_date was not returned by either build.
    * response_deadline ("last date to apply") did not exist as a column.

  Migration 073 therefore:
    1. adds t_contracts.response_deadline (DATE, nullable) — the last date to
       submit a quote. Enforced later in rfq_submit_quote; shown to vendors as
       "respond by" in the create flow (batch 2).
    2. adds start_date + response_deadline to BOTH list builds, and vendors_count
       to the grouped build too, so List and By-Vendor agree.

  The whole function body in 073 is the LIVE definition pulled with
  pg_get_functiondef, with ONLY those keys inserted — nothing else retyped or
  reordered — so it cannot drift from what prod runs.

  Aging is computed client-side (today vs response_deadline); the server only
  carries the date.
