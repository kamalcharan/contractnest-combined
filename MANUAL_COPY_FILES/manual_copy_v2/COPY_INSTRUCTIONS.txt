🆕 NEWEST — Billing-count semantics fix + toast readability
─────────────────────────────────────────────────────────────────
Raised on the 18-visits/every-18-days/Monthly/1-year config: the gate
hard-stopped a config that is business-reasonable. Root cause: the
billing engine conflated two meanings of quantity — visit count vs.
bill count. Owner-approved fix:

  - contractnest-ui/src/utils/service-contracts/contractEvents.ts
  - contractnest-api/src/services/contractEventsDerivationService.ts
    (BOTH copies changed in lockstep — and this repaired a pre-existing
    silent parity break: the API copy still term-derived every recurring
    count and lacked the last-installment rounding absorb; both are the
    missed back-ports of the UI's earlier "×12 Monthly" fix.)
    New rule in the recurring-billing branch:
      · visit-generating block (service category + service cycle):
        quantity = VISITS; bill count = round(term ÷ billing period) —
        "18 visits, monthly, 1 year" = 12 bills of total/12. ROUND not
        ceil (ceil would make monthly-in-a-year 13 bills, quarterly 5).
      · fee/billing-only or non-visit block: quantity = bill count,
        exactly as before (BBB fee blocks byte-unchanged).
    Gate updated to match: billing-leg check skipped for visit blocks
    (their bill count now always fits by construction); service-leg
    check unchanged. The 18×18d/Monthly/1-year config now passes.

  - contractnest-ui/src/components/common/toast/VaNiToast.tsx
    Toast message no longer truncates to one ellipsized line
    (truncate → break-words); title untouched, all other toasts
    unaffected (short messages still render on one line).
  - contractnest-ui/src/components/contracts/ContractWizard/index.tsx
    The two cadence-gate toasts now show for 10s (default was 4s).

EARLIER — Cadence-fit wizard gate (CN-1002 root-cause fix)
─────────────────────────────────────────────────────────────────
Root cause traced on CN-1002: the wizard accepted a self-contradictory
config — 14 × 30-day cycles inside a 1-month contract — and three
engines each resolved it differently: pricing billed the full quantity
(invoice ₹9,150), billing events truncated at contract end (only 2 of
14 cycles = ₹1,200 scheduled), service events have no end-clamp at all
and would overrun. Fix: the wizard now REFUSES the config.

  - contractnest-ui/src/utils/service-contracts/contractEvents.ts
    New exported computeCadenceViolations() — lives in the same file as
    the event math so the gate can never drift from what the engines
    actually do. computeContractEvents itself is UNTOUCHED (the parity
    contract with contractEventsDerivationService.ts is unaffected).
    Fit rule per block (quantity > 1, not unlimited):
      service leg: (qty−1) × serviceCycleDays must fit the duration
      billing leg ('defined' mode, recurring cycles only, cadence-priced
        blocks excluded — they derive count from duration and clamp):
        (qty−1) × cycle periodDays must fit the duration

  - contractnest-ui/src/components/contracts/ContractWizard/index.tsx
    Two gates in handleNext, both following the existing unified-cycle-
    mismatch pattern (error toast + return, user cannot proceed):
      1. On the blocks step — early feedback where quantity is editable.
      2. Backstop before ANY submission (covers the edit-from-review
         shortcut that jumps details → review without re-passing blocks,
         and runs before the auto-accept pre-payment dialog too).
    Toast: '"<block>": N billing cycles of X days span ~Y days, but the
    contract runs Z days. Reduce the count, shorten the cycle, or extend
    the contract duration.'

  Field names verified against ConfigurableBlock (serviceCycleDays,
  customCycleDays, unlimited, config.billingOnly all exist). Could not
  run tsc in the session sandbox (no node_modules) — a TS error would
  surface in Vite's dev overlay immediately on start, not silently.

  NOT fixed (out of scope, noted): CN-1002 itself is unfixable by code —
  its stored config IS the contradiction. The silent `date > endDate`
  truncation inside the billing engine and the missing end-clamp in the
  service engine remain as-is; the gate makes them unreachable via the
  wizard, but other payload sources (bulk-assign items, RFQ-to-contract
  later) would still bypass a UI-only gate. A DB-side backstop belongs
  in create_contract_transaction_v2 eventually — flagged, not built.
