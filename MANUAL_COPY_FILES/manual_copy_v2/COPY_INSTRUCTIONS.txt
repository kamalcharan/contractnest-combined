What Sprint 3 found, worth knowing before you look at any of this:
  - Traced the real call graph: there are 3 shapes, not 5 as originally
    scoped. "Template Assign" isn't a separate pathway — it's the same
    POST /api/contracts endpoint as the Wizard, just with template_id
    pre-filled. Bulk Assign loops that identical endpoint per buyer.
    Plan Subscription and Top-up are the only structurally different
    ones — direct RPC-to-RPC calls into create_contract_transaction,
    bypassing the API/edge layer entirely.
  - Checked the Wizard's mapWizardToRequest and gating.ts: buyer_id is
    reliably present by submission time (step-gated), same for Bulk
    Assign (set directly per selected contact). Neither ever sends
    seller_id — harmless, since V1 always hardcoded seller=tenant.
  - BIG ONE — Revenue vs. Expense mode. The wizard already has this
    concept via contract_type: 'client'/'partner' (Revenue — tenant is
    seller) vs. 'vendor' (Expense — tenant is BUYER, the picked
    counterparty is the seller). EquipmentStep.tsx:96 confirms this
    (`addedByRole = contractType==='vendor' ? 'buyer' : 'seller'`), and
    the finance layer already relies on it (scanner classifies every
    billing event payable-vs-receivable by `contract_type='vendor'`,
    get_tenant_payables is commented "the buyer mirror: my own
    vendor-contract[s]"). But create_contract_transaction (V1) NEVER
    reads contract_type for this — seller_id is unconditionally
    tenant_id, buyer_id is unconditionally whatever contact was picked.
    So every 'vendor'-type (Expense mode) contract today has
    seller/buyer inverted: the vendor (actual seller) is stored as
    buyer_id, and the tenant (actual buyer) is stored as seller_id.
    This also means the CNAK grant goes to the wrong party (vendor
    gets buyer-portal access on a contract where they're actually the
    seller). Explicitly NOT fixed yet — this needs a decision on
    whether create_contract_transaction_v2 resolves seller/buyer from
    contract_type internally, or keeps explicit params and pushes that
    resolution onto each caller. Parked per instruction: RFQ /
    buyer-initiated contract creation is low priority until that space
    is actually entered — this finding will matter once it is.
  - purchase_topup_template_v2 could not be end-to-end tested against a
    real topup pack: the only published "Wallet Top-up (₹1,000)"
    template in the catalog has no `metering` config on its blocks at
    all, so it fails NOT_A_TOPUP_PACK — identical to what V1 would do,
    since the gate was copied verbatim. Pre-existing catalog data gap,
    not a V2 bug. subscribe_tenant_to_plan_v2 WAS tested end-to-end
    successfully (real "Free" plan, test tenant, full contract + CNAK
    grant + JTD insert all landed correctly, cleaned up after).

Already applied live to the Supabase project — all three functions
