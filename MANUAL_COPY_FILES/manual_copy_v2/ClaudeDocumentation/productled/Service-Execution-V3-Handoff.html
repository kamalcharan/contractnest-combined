Tier 1 — CTA link (build with Sprint 7)

  • Template messages with a URL button; the "form" is our own mobile page behind a CNAK-style token — the exact drawer from screen 2, responsive.
  • No 24-hour window constraint (approved templates), works on every device, photos & multi-asset gating fully supported.
  • Outbound = n_jtd message rows; delivery via existing jtd-worker → MSG91 → webhook chain.

Tier 2 — in-chat buttons (fast follow)

  • Quick-reply buttons for light choices (confirm slot / reschedule). Replies are inbound messages — needs the inbound webhook wired (today MSG91 posts to n8n only; forward to msg91-webhook, already recommended in CLAUDE.md).

Tier 3 — WhatsApp Flows (the smartform itself CAN live here)

  • Meta's native multi-screen forms inside the chat — and Flow JSON includes PhotoPicker (camera/gallery, min–max count) and DocumentPicker, so the technician's checklist with photo proof fits: checkpoints → pass/fail radios, readings → number inputs, photo screen last (pickers can't share a screen).
  • Compile, don't hand-build: a "Publish to WhatsApp" action compiles each approved m_form_templates version into Flow JSON and stores its flow_id — form versioning maps to Flow versioning.
  • One Flow = one proof card (event × asset). The visit gate, placeholder locks and next-card sequencing stay server-side — a locked card simply never gets a Flow sent. WhatsApp is a second client of the same engine, not a second engine.
  • Photo responses arrive encrypted — a one-time download-and-decrypt pipeline lands them in t_service_evidence; the answers land in m_form_submissions (source: whatsapp_flow).
  • Key MSG91 verifications: Flows with media-upload components pass through intact (payload + decryption keys), Flow JSON version supported, Flows creatable via API. New templates are positional params (the documented trap). Tier 1 CTA-link ships first regardless.

Mobile rules

  • One screen, one decision. List view or one form — never panes. Thumb-reach targets ≥44px, submit pinned at the bottom.
  • Auto-advance: submitting AC-101 lands you straight in AC-102's form with a "proven ✓" toast — the 3-AC visit is one continuous run (~30s per unit).
  • Camera-first: photo button invokes the native camera (capture attribute); no file-browser detours.
  • Poor-signal tolerance: submissions queue locally and sync when back online — basements and terraces are the normal case, not the edge case.
  • Prefill statics, never proof: the next unit's form pre-carries context (visit, block) but readings and photos always start empty — copy-forward would forge evidence.
  • Same routes, same writes as screen 2 — this is a responsive rendering, not a second app.

Default template — when no smart form is bound

  • Resolution ladder, final rung added: block form → KT form → contract fallback → platform default: "General Service Completion" (seeded once, versioned like any form).
  • 3 fields, ~5 seconds: work status (completed / partial), asset condition (OK / needs attention), optional note — photo appended if require_upload.
  • So policy smart_form always yields a form (never a dead end); policy none stays a one-tap done. The filter card here demonstrates the default form.
