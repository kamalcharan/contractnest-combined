The JTD Nucleus

Jobs To Do was designed in December 2025 to be the single spine every commitment in ContractNest flows through — billing, service visits, appointments, group sessions. It shipped as a notification log instead. This is the plan to finish building what was already designed, without touching anything currently running.

00 · Executive summary

Nothing here is broken. It's unfinished.

An audit across contract creation, appointments, service tickets, evidence, invoicing, CNAK access, and group sessions found the same failure shape repeating: individually well-built pieces, wired to nothing that enforces they connect. 238 contracts exist in this database. Not one has gone from creation → claimed → serviced → evidenced → invoiced → paid through a real, enforced mechanism.

Tracing JTD's own history explains why: it was designed on 17 Dec 2025 as exactly the spine this needs — "every significant action in ContractNest flows through JTD" — shipped its first use case five days later, and every commit since has widened that one slice (notifications) instead of returning to the other six event types the design named. n_jtd_event_types still holds appointment, service_visit, and task as valid rows, live in production, completely unused.

This document is the plan to finish it: build new, versioned (v2) API/Edge functions alongside the existing ones — nothing currently running gets modified — prove it end-to-end on real contracts, then migrate BBB deliberately and last.

02 · Designed vs. shipped

The nucleus was never missing. It stalled.

The founding document is unambiguous, eight months before this audit:

"JTD is NOT just a notification system - it's a unified framework that handles: Notifications, Appointments, Tasks, Service Visits, Reminders, Payments, Documents. Every significant action in ContractNest flows through JTD. When a contract is created with 12 monthly services, JTD automatically creates 12 service_visit records." JTD-Framework.md · v1.0 · 17 Dec 2025 · Status: Architecture Finalized

Section 3 of that same document, titled VaNi Integration, states the framework is API-first specifically so an AI agent can execute jobs directly against it — this was never conceived as a human-facing log.

03 · Target architecture

JTD becomes the spine. Everything else becomes detail.

Not everything maps into JTD — CNAK is a permission grant, not a commitment, and stays fully separate. The rest reorganizes around one rule: JTD owns what's owed and its state; every other table owns how it was actually carried out, linked back by a real foreign key.

04 · The commitment lifecycle

Appointments are conditional, not universal

Billing commitments never need an appointment. Group-session commitments never need one. Service commitments sometimes do — the rule is per-industry, deliberately left open for now. The state flow has to branch here, not assume every commitment passes through the same stages.

Enforcement, not duplication. n_jtd_status_flows already exists as real infrastructure for governing valid transitions. It's used to make invoiced a hard prerequisite before anything downstream can claim paid — closing the exact gap that produced 40 contracts with fabricated payment history — without JTD growing its own shadow copy of payment status.

05 · Contract creation

One real INSERT. Five callers. One missed hook.

Every pathway that can create a contract was traced in source, not assumed. There is exactly one SQL statement that inserts into t_contracts — create_contract_transaction. Everything else is a different caller of that same function.

Bulk Assign is almost certainly how BBB's 49 contracts were created — relevant to the eventual BBB-sync step, since it confirms the pathway BBB actually runs through.

Two things that turned out not to be real pathways, worth removing from scope: contract renewal/clone is 100% mock UI with a literal // Mock renewal data comment and no API call anywhere; and RFQ Award creates nothing — the state converted_to_contract exists in the schema but nothing in the codebase ever sets it.

06 · V2 build strategy

New, versioned, parallel. Nothing existing touched.

New API routes and edge functions, tagged v2, sitting fully alongside what's running today. Old pathways keep serving all current traffic unmodified — which is also what keeps BBB structurally safe without anyone having to be careful about it.

Reused patterns — already proven in this codebase

  • Idempotency — the scanner's own appointment step already does NOT EXISTS checks plus catches unique_violation as a no-op. Same shape applies to JTD commitment creation.
  • Race conditions — version-based optimistic locking already exists on the tables that matter; the scanner already uses pg_try_advisory_xact_lock + FOR UPDATE SKIP LOCKED to stop overlapping runs colliding.
  • Self-healing uniqueness — the invoice-number generator's retry-to-1000-attempts pattern is the template for anything V2 needs a guaranteed-unique code for.

What's genuinely new

Idempotency at the whole-chain level: one new SECURITY DEFINER function per creation pathway, wrapping contract + events + JTD commitments in a single Postgres transaction — a retried call either produces the full chain exactly once, or nothing at all.

Working discipline — non-negotiable

  • Every branch of work anchors to a tag. v1.0.0 is the baseline; a tag is cut again at minimum at the confidence gate and before BBB migration. Code changes are always made and reviewed relative to a known tag, never floating against an untagged branch tip.
  • V2 files keep their V1 name, plus the identifier. No new naming scheme — contractController.ts → contractControllerV2.ts, create_contract_transaction → create_contract_transaction_v2. The nomenclature stays recognizable so the two implementations are obviously paired, not two unrelated pieces of code.
  • Confirmation triggers removal, not deprecation. Once you've tested a V2 pathway and confirmed it working, its V1 predecessor is deleted in that same change — not left dormant "just in case." This is a direct lesson from §02: JTD's own dormant scaffolding sat unremoved and unfinished for eight months. Nothing in this initiative repeats that shape.
  • Cutover happens inside the API, not the UI. Route paths the UI already calls stay identical; internally, the handler switches from the V1 implementation to the V2 implementation once that pathway is proven. See Fig. 5.

08 · Phased rollout

No merge to main unless mandatory

Everything through the confidence gate lives on a branch. v1.0.0 is already tagged on master as the pre-initiative baseline — if anything in production needs fixing while this work is in flight, it's resolved against that tag, independent of whatever state this branch is in. Every phase below starts from a known tag and cuts its own before handing off to the next — a rollback point always exists behind whatever is currently in flight.

  1. Phase 0 · Milestone 1

    Evaluate JTD maturity

    Confirm exactly what's live vs. dormant in the master tables — event types, source types, status flows — before writing anything new on top of them.

  2. Phase 1 · Milestone 1

    Contract + template foundation, V2

    The basic fundamental correction everything else depends on. One new atomic RPC (create_contract_transaction_v2) with every real pathway — wizard, template, bulk, plan sub, top-up — repointed to it one at a time. Templates are proven here as a variant of this same pathway, not a separate one: the wizard-seed path must produce identical JTD output to a from-scratch contract. Business-model templates (the pre-built starting points a tenant's own catalog is seeded from) ship as part of this milestone, not after it.

  3. Gate

    Confidence checkpoint

    Once the contract + template foundation is solid, everything else — RFQ, appointments, tickets, evidence, invoicing, product-led UX — stitches onto the same spine with comparatively little friction. Test against at least 25 real contracts before trusting it.

  4. Phase 2

    BBB migration

    One-time backfill + one additive line in the schedule-generation RPC. See §09.

  5. Phase 3 · Milestone 2

    Stitch-in, alongside product-led UX

    RFQ's vendor-authored contract flow (greenfield), appointments, tickets, evidence, and invoicing all wire against the now-proven spine — starting in step with the product-led UX evolution, not after it. Each V1 pathway is retired the moment its V2 replacement is confirmed working, one at a time, never as a single cutover, and never left running dormant alongside its replacement.

09 · BBB safety guarantees

BBB is touched exactly once, at the end, on purpose

  • ✓ No table BBB depends on — t_group_session_schedule, t_session_attendance, t_session_payment_declarations, any gs_* RPC — is written to by any phase before the gate.
  • ✓ BBB's billing and notification triggers keep running through the existing pathway the entire time.
  • ✓ Migration is a pure insert: one JTD row per existing occurrence, pointing at it — nothing about roster or attendance is read-write.
  • ✓ Going forward, exactly one additive line in the schedule-generation RPC — new occurrences get a JTD row the moment they're created.
  • ✓ A standing acceptance check — count of t_group_session_schedule rows vs. matching JTD rows for BBB's tenant — run continuously, alerting the moment they diverge. The same mechanism that would have caught the tax-RPC drift and the Taxes NAV disappearing, this time applied to the one thing that must never silently drift again.

11 · Sprint-wise POA

Two milestones. The first unblocks the second.

First-pass shape, not committed dates — sprint sizing gets real once Phase 0's maturity evaluation is actually done. What's fixed is the sequencing: Milestone 1 is the foundation correction in contracts and templates; Milestone 2 doesn't start until that foundation is proven at the confidence gate, and then runs in step with the product-led UX evolution rather than after it.
