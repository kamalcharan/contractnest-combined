1. ONE THEME FOR THE WHOLE FLOW
───────────────────────────────
  You were seeing three identities in one journey:

    express screens   their own paper-and-green palette (--deep #0B5F4E),
                      a serif headline, and a dark-mode variant
    VaNi tail         hardcoded orange — VaniWorkingStep, Screen8APricingStep,
                      TermsConditionsStep and LovSetupStep each define
                      VANI #ff6b2b / TEXT #1a1816 / BG #f7f5f2 as constants,
                      light only, no theme lookup at all
    header chrome     whatever theme the tenant happened to have

  The header drifted because the long flow applies the VaNi theme in
  VaniIntroStep and again in VaniConsentStep — and express skips both.

  Fixed on both sides:

    * express.css now carries the VaNi tokens VERBATIM from those step files.
      Same orange, same ink, same paper, same borders.
    * The serif headline is gone; the VaNi steps use the system stack.
    * The dark-mode block is gone. Deliberate: the VaNi steps have no dark
      variant because their palette is hardcoded, so a dark express screen
      handing off to a permanently light pricing screen was the single most
      jarring transition in the flow. Matching the destination beats being
      individually nicer.
    * ExpressShell calls setTheme('vani') on mount, so the OnboardingLayout
      header matches from the very first screen through to done.

  setTheme only writes localStorage — it does NOT touch preferred_theme on the
  user record (only ThemePreferences and Header do that), and ThemeContext
  re-reads preferred_theme from user_data on the next login. So this is
  exactly what the long flow already did, nothing is permanently overwritten.

3. "WE'LL ACTIVATE YOUR LINE OF BUSINESS" — THE ASIDE CARD
──────────────────────────────────────────────────────────
  Before this, a seller could not even SEE equipment without a Knowledge Tree:
  the list was filtered to selectable items, matching ResourcePickStep's rule
  that a seller's equipment needs a KT because that is what becomes priced
  catalog blocks.

  Hiding it was the wrong answer. The tenant genuinely services that
  equipment, and that is exactly what we want to know. So now:

    * Everything is listed and pickable.
    * "Ready" badge marks the ones that arrive with a KT.
    * Picking one that has no KT shows a panel on the right naming exactly
      what they picked, thanking them, telling them to carry on, and
      promising activation "usually within 12 hours, often much sooner".
      Naming the equipment matters — a generic "we'll get back to you" reads
      as a brush-off.
    * The tile itself goes dashed-outline rather than solid orange, so the
      difference between "building this now" and "building this for you" is
      visible at a glance without a word of explanation.

  WHAT THE SEEDER RECEIVES
  Only the buildable set. Equipment awaiting activation is held back — it has
  no KT, so passing it in would seed nothing and reproduce the exact "no
  service blocks found" failure from Sprint 2. It is recorded, not seeded.

  WHO IS AFFECTED
  Only equipment, only for sellers (and 'both'). Facilities and services need
  no KT — they seed as registry nodes and shell blocks — and a buyer's
  equipment goes to the asset registry. None of those ever wait on us.

  IF EVERYTHING PICKED IS AWAITING ACTIVATION
  Seeding would run on empty arrays, so the flow takes ResourcePickStep's own
  documented Skip route (ResourcePickStep:252) straight to lov-setup — the
  path it already uses for a business the catalog does not model yet. Proven
  code path, not a new one. The button reads "Continue" instead of "Build my
  workspace" in that case, because there is nothing to build yet.

  HOW ADMIN FINDS THE QUEUE (no schema change, works today)
  The picks are written to t_tenant_selected_resources exactly as before —
  including the ones awaiting activation, because that table is the tenant's
  stated intent. "Awaiting activation" is derivable:

    select tn.name as tenant, rt.name as item, rt.resource_type_id,
           rt.industry_id, s.purpose, s.selected_at
    from t_tenant_selected_resources s
    join m_catalog_resource_templates rt on rt.id = s.resource_template_id
    join t_tenants tn on tn.id = s.tenant_id
    where s.purpose = 'sell'
      and rt.resource_type_id in ('equipment','consumable')
      and not exists (select 1 from m_equipment_variants v
                      where v.resource_template_id = rt.id and v.is_active)
    order by s.selected_at desc;

  It is ALSO written explicitly into t_tenant_onboarding.step_data under
  resource-pick as `pending_activation: [{template_id, name,
  resource_type_id, industry_id}]`, so the queue survives even if that
  derived query is ever unavailable.

  THE WHATSAPP NOTIFICATION IS NOT BUILT — as you said, later. When it is,
  `pending_activation` in step_data is the hook to read: it already carries
  the tenant, the item names and the industry.
