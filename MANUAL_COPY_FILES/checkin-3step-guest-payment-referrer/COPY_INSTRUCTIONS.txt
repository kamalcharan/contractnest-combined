UPDATE -- UPI "Pay now" fix (same batch, updated in place)
---------------------------------------------------------------
Finally root-caused the GPay "Payments to this receiver are not allowed
by UPI network" error from way back. The Karnataka Bank poster QR you
shared confirmed it: that's a real bank-signed merchant QR (BHIM/KBL,
signed by the bank's PSP with a private key). Our own "Pay now" button
and its "Or scan to pay" QR were both built from a hand-constructed,
UNSIGNED upi://pay link -- only the bank/PSP can produce a valid
signature, so GPay was rejecting ours outright while the real bank
poster (properly signed) scans fine. No URL parameter fixes this --
mc=0000 never could have.

Removed both the broken "Pay now" button and the broken self-generated
QR entirely (a QR encoding the same unsigned link would have failed
the same way). Replaced with: the UPI ID shown plainly with a Copy
button, plus 3-step instructions to open GPay/PhonePe/any UPI app,
choose "Pay to UPI ID," and pay manually. This works because the
member's own UPI app is now the one constructing and signing the
request as a first-party participant -- not us handing it an external
unsigned link. Same mechanism as scanning the bank's real QR, just
typed instead of scanned. The UPI-reference entry field (already
built) is unchanged -- still how the chair finds out you paid.

Also cleaned up now-dead code that only existed to support the broken
flow: the "Before you pay" confirm modal, the QrCode import, and the
upiPayUrl() builder. tsc/eslint re-checked clean after removal.

UPDATE -- garbled character fix (same batch, updated in place)
---------------------------------------------------------------
You reported seeing "strange characters" on the live page -- real bug,
not a screenshot artifact. Root cause: this file has had CP437 mojibake
baked into it for a while (predates this batch entirely) -- somewhere
along the way, UTF-8 bytes for things like em dashes, checkmarks, and
emoji got misread one byte at a time as the old DOS/Windows-console
"OEM" codepage (437) and re-saved that way -- each real character
(an em dash, a checkmark, an emoji) turned into 2-4 garbled letters in
its place, exactly what you circled in the screenshot.

Confirmed and fixed every instance in SessionCheckinPage.tsx (25 em
dashes, 42 decorative separator characters, checkmarks, arrows, the
rupee sign, the guest/substitute emoji, all restored to real UTF-8).
Verified: file now has zero remaining garbled sequences, tsc still
shows zero errors, eslint shows the same (pre-existing, unrelated)
warnings as before. useSessionCheckin.ts checked too -- it was clean,
no corruption there.

Not touched: this same corruption pattern may exist in OTHER files
across the codebase (it's a save/tooling issue, not specific to this
page) -- flagging that as a separate thing worth a broader sweep if
you want one; out of scope for this batch, which only covers the
check-in files already being changed here.

UPDATE -- race-condition fix added (same batch, updated in place)
---------------------------------------------------------------
You asked directly: "i hope there are no race conditions on this
form...... previously we got 2-3 entries at a time recorded
(Especially payments)". Checked, and you were right to ask -- found
it's still a real gap:

- There was NO unique constraint on t_session_payment_declarations at
  all. Confirmed live: right now there are 3 pending declarations for
  the same due for one member, and 2 for another -- pre-existing, not
  caused by anything in this batch. Per your call, these are left
  alone (chair rejects the extras manually next time they're on
  Payments to confirm).
- Added migration 052_checkin_payment_declaration_dedup.sql: two
  partial unique indexes (one pending declaration per member+due, one
  per guest+service+session) plus ON CONFLICT DO NOTHING on every
  payment-declaration insert (gs_submit_checkin x3, gs_checkin_guest
  x2). A resubmit or double-tap can no longer create a second row --
  the DB silently no-ops the duplicate insert. Already applied live.
- Added a client-side guard too (SessionCheckinPage.tsx, submitLockRef):
  React state updates aren't synchronous, so a fast double-tap could
  fire submit() twice before the "submitting" state disables the
  button on screen. A ref is checked/set synchronously, closing that
  gap on the very first click, not just the re-render after it.
- SessionCheckinPage.tsx in this folder already has both fixes baked
  in -- it's the same file as before, just updated in place. If you
  already copied the pre-race-fix version, copy it again to get this.

WHAT THIS IS (original batch)
---------------------------------------------------------------
Implements the 3-step check-in redesign we mocked up and agreed on
(Identify -> Payment -> Check-in), plus everything that came out of
the audit thread:

1) Identify is now its own step -- no more auto-populated identity
   bleeding into payment/attendance. Uses the exact same phone-entry /
   not-found guest-or-substitute / device-recognition flow as before,
   just laid out as step 1 instead of interleaved with attendance.

2) Payment is its own step, and now branches correctly by identity:
   - Member (or a substitute standing in for one): the real "Your
     dues" card, same as before.
   - Guest: NO LONGER shows the member dues card (that was a bug you
     caught -- a guest with no contract was seeing a fake dues
     screen). Guests now pick from standalone catalog services the
     tenant flags guestPayable -- nothing hardcoded. Your existing
     "Guest Participation Fee" (Rs.600) shows up here automatically;
     add more anytime by setting config.guestPayable: true on any
     other service-category catalog block.
   - Substitute: no payment step at all (matches gs_checkin_substitute
     today -- it only ever recorded attendance, never a payment; that
     wasn't changed here).
   - A ContractNest platform brand card sits above the tenant's own
     branding on every screen (blue, "Secure session check-in", a
     Verified badge) -- the "brand propagation" card you asked for.

3) Guest "Referred by" -- a required search-and-select field (typing
   filters real roster members, tenant + membership scoped) in the
   guest quick-details form. Tags which member brought the guest.

4) "Payments to confirm" fix -- solved going forward. Root cause was
   confirmed from your own audit: payEventId/selectedServiceId
   auto-populate just so the "current due" / "pick a service" card can
   render -- they were never a signal that the member/guest actually
   wants to pay. submit() now only creates a payment declaration when
   there's a real signal: tapping "Pay now" (opens UPI) or typing a
   UPI reference. Simply checking in with an open due sitting there no
   longer creates a phantom pending declaration. This supersedes the
   earlier checkin-payment-declaration-fix batch (still sitting
   uncopied in that older folder) -- that fix is now folded into this
   file; you can ignore/delete that older batch, nothing further
   needed from it.

IMPORTANT -- guest fees are TRACKED-ONLY, not in the ledger yet
---------------------------------------------------------------
This was a deliberate scope call (asked you, you picked "track-only
for now"): confirming a guest-fee declaration marks it confirmed, same
as any other declaration, but does NOT create an invoice or revenue
entry -- there's no real contract for it to settle against. It's
recorded as check-in data, not accounting data. If/when you want real
ledger integration for guest fees (a lightweight walk-in-sale/invoice
path), that's separate follow-up work, flagged for later.
