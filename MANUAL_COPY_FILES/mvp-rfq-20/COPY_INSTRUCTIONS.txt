WHAT THIS SOLVES
─────────────────────────────────────────────────
User's correction on the earlier "recommender" plan: the Contract wizard
recommends from the TENANT'S OWN catalog (VaNi/recommend.ts — a seller
reusing their own priced service blocks). An RFQ is the buyer asking an
EXTERNAL VENDOR to quote — recommending the tenant's own catalog doesn't
apply there. What RFQ should recommend from is the Knowledge Tree (KT) —
admin-curated master data per equipment type.

Researched KT properly using DG Set (Generator) as the concrete example
(m_catalog_resource_templates id d8a5de1b-e110-4b70-8542-081e56ecba1e):
  - m_equipment_variants: 10 capacity-based variants (1-10 kVA up to
    500-2500 kVA industrial).
  - m_equipment_checkpoints: 95 checkpoints across ~30 sections
    (Battery & Starting System, Cooling System, Power & Electrical, etc.),
    each tagged with a service_activity (pm / repair / inspection / install
    / decommission).
  - m_service_cycles: the useful layer for this feature — named, cadenced,
    PRICED service packages via catalog_name, e.g. "DG Set Preventive
    Maintenance — Standard Scope" every 30 days, INR 1,500-6,000 median
    3,000; "...Electrical Systems" every 90 days, 2,500-11,000; "...Output &
    Performance" every 90 days, 3,000-12,000; "...Comprehensive Scope"
    every 365 days, 8,000-40,000. Plus finer per-section cycles (some
    hour-based, e.g. Cooling System every 250 hours) and one-off visit-based
    checkpoints (install/repair/decommission, frequency_unit='visits').

Two things verified before writing any code:
  1. Access — the knowledge-tree edge function's GET routes (summary,
     cycles, variants, coverage, etc.) do NOT check isAdmin; only the
     POST/write routes (save, delete, tag-compliance, equipment-meta,
     snapshot) do. Confirmed by reading contractnest-edge's
     supabase/functions/knowledge-tree/index.ts directly, and separately
     confirmed by the user: onboarding already reads KT data with no admin
     requirement.
  2. The missing link — a tenant's own Resource (what fills the RFQ's
     "What does this cover?" coverage list) has NO real foreign key to
     m_catalog_resource_templates. t_tenant_selected_resources only records
     which templates a tenant bulk-selected at onboarding, not a per-resource
     mapping (checked live: joining by tenant_id alone fans out to every
     selected template, not a 1:1 link). So resolving "this coverage line's
     resource -> which KT template" is done by NAME MATCH (case-insensitive,
     bidirectional substring) — the same fuzzy approach the Contract
     wizard's own recommend.ts already uses for its VaNi banner. Not a new
     pattern, but not a clean FK either — flagging so it isn't assumed to be
     more precise than it is.

Layout, per explicit direction this session: the RFQ builder's Scope step
was a single centered column (max-width 640px). Restructured to two columns
for that step only (other steps unchanged): main request content on the
left (flex '1 1 480px'), Knowledge Tree suggestions sidebar on the right
(flex '0 1 300px', sticky), wrapped in a flex-wrap row so it naturally
stacks on narrow viewports (no media query needed, this file uses inline
styles throughout, not Tailwind). Outer container widens from 640px to
980px only when stepId === 'services'.

Files Changed:
  - contractnest-ui/src/components/catalog-studio/BlockCardConfigurable.tsx
      Added optional ConfigurableBlock.config fields: ktCycleId,
      ktPriceMin/Median/Max, ktPriceCurrency — tags a block as created from
      a specific m_service_cycles row (dedupes "already added" suggestions)
      and carries the KT price range for reference display. Never written
      into price/totalPrice — the vendor still quotes that.
  - contractnest-ui/src/pages/contracts/rfq/RfqBuilderPage.tsx
      - New imports: useResourceTemplates (existing hook, GET /api/resources/
        resource-templates), useKnowledgeTreeSummary (existing hook, GET
        /knowledge-tree/summary), getCurrencySymbol.
      - matchTemplateFor(resourceName): resolves a coverage line to a KT
        resource_template_id by fuzzy name match against up to 100
        templates for the tenant's resource_type_id (equipment/asset).
      - addedKtCycleIds: a Set derived from services[].config.ktCycleId, so
        an added suggestion stops showing.
      - addFromKT(coverageLine, cycle): adds a real Service FlyBy block
        immediately (same shape as any manually-added block, no
        preview/staging) — name = catalog_name (fallback checkpoint_name),
        serviceCycleDays = frequency_value, coverageTypeId linked to the
        coverage line, price 0 (vendor quotes), KT price range carried in
        config for reference only.
      - New KTSuggestionsForCoverage component (same file, defined after the
        page component): one per coverage line, calls
        useKnowledgeTreeSummary for that line's matched template, filters to
        frequency_unit==='days' only (hour/visit-based cycles don't map to
        a days field, so they're skipped rather than mismapped), dedupes by
        catalog_name+frequency (or checkpoint_name+frequency when
        catalog_name is null), sorts by cadence, renders a compact card per
        suggestion with an "Add to request" action.
      - Scope step restructured into the two-column layout described above.
