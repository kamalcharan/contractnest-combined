THE DESIGN DECISION IN THIS BATCH — two namespaces, two rules
  The spec says deny all direct client access. That is right for contract
  evidence and wrong for identity assets, and the live data proves it:
  ContractDocument, PublicPaymentSection, the invoice views and 85 call sites
  in total render a tenant logo from a DURABLE url. A 5-minute signed url
  cannot serve a contract PDF emailed to a buyer, or a public review page
  opened three days later.

    contracts/**  private. Brokered reads only, signed per viewer, minutes.
    tenants/**    public read, no write. Logo, avatar, block icon, payment QR.

  These are public by nature — the logo is already on every invoice and on the
  unauthenticated review page; the QR is printed and stuck on a desk. Nothing
  confidential moved. Writes are denied everywhere; the Admin SDK bypasses
  rules and is the only writer.

WHAT MOVED
  UI, via the batch-C hook (useUploadIdentityAsset):
    AvatarSection.tsx        user avatar
    PersonalInfoSection.tsx  the same avatar on the other surface
    IconPicker.tsx           catalog block custom icon
  Each now uploads to tenants/{tenant}/{kind}/… , is NOT metered against the
  evidence quota, and gets back the durable url it already stored. Their
  layouts are untouched — these surfaces needed their storage path changed,
  not their controls.

  Server-side, keeping their routes and contracts EXACTLY as they were:
    tenantProfileService.uploadLogo   POST /api/tenant-profile/logo
    integrationService.uploadQrImage  POST /api/integrations/upload-qr
  Both now write through the Admin SDK into tenants/… with a registry row,
  instead of the Firebase client SDK with signInAnonymously() and a stored
  getDownloadURL() token. The multipart contract and the response shape are
  identical, so both UI callers (useTenantProfile, TenantContext) and the
  integrations form are unchanged.

  ⚠️ The QR endpoint's DECODE LOGIC IS UNTOUCHED. It is what recovers org_id
  and mcc from the bank's own sticker, and those two fields are the entire
  reason UPI merchant payments work at BBB. Only where the bytes land changed.

WHAT DID *NOT* MOVE, AND WHY
  · Service evidence (TicketEvidencePanel) — the upload cannot be migrated
    alone. get_service_ticket_detail, _report and _list all READ
    t_service_evidence, so moving the write without the reads would make new
    evidence invisible on the ticket. It goes with those reads in batch F,
    where the category bug and the two decorative dropzones are also fixed.
  · /settings/storage pages and the two old FileUploaders — the cleanup batch.
  · Nothing was deleted. The legacy stack still works, untouched, so this
    batch is reversible by copying the four original files back.

⚠️ DO NOT DEPLOY storage.rules YET — now blocked until batch F, not D
  Three surfaces still upload through the legacy /api/storage path, which uses
  the client SDK and IS governed by these rules: the service-evidence panel,
  the /settings/storage pages, and the two old FileUploaders. Deploying now
  would break them.

EXISTING FILES ARE SAFE
  The 2 live tenant logos and 2 live QR images are firebasestorage.googleapis
  .com urls carrying an access token. Those tokens authorise independently of
  rules, so every existing asset keeps rendering after the rules deploy. Only
  NEW uploads take the new path.

STEP 2b: ⚠️ APPLY BUCKET CORS — needed before /settings/upload-lab works
─────────────────────────────────
The browser PUTs bytes straight to Google Cloud Storage using a signed url.
A Firebase Storage bucket ships with NO CORS configuration, so the browser
blocks that request before it is sent. This was never hit before because the
Firebase client SDK talks to endpoints that are already CORS-enabled.

  cd contractnest-edge\firebase
  gcloud storage buckets update gs://contractnest-driveapp.firebasestorage.app `
    --cors-file=cors.json

  # older toolchains:
  # gsutil cors set cors.json gs://contractnest-driveapp.firebasestorage.app

Verify:
  gcloud storage buckets describe gs://contractnest-driveapp.firebasestorage.app `
    --format="default(cors_config)"

NOT needed for anything in batch D itself — the logo and QR endpoints upload
multipart to OUR api and the server writes to storage, so no browser-to-GCS
request is involved. This is only for the browser-direct path from batch C
(the upload lab, and the service-evidence panel once batch F moves it).

SYMPTOM IF MISSING: the upload bar reaches ~15% and stops, with a CORS error
in the browser console on a storage.googleapis.com PUT — no server error,
nothing in the api log, nothing in Sentry. It reads like a code bug and is not.

See contractnest-edge/firebase/README.md for editing the origin list.
