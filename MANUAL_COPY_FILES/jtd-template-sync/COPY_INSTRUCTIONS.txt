WHAT THIS MIGRATION ADDS
  fn_jtd_template_sync(p_tenant uuid default null, p_dry_run boolean default false)

  Solves the gap eager copy creates: before per-tenant rows existed, wiring a
  GLOBAL template reached every tenant instantly via fallback. Once a tenant
  owns a row, the tenant row WINS and a global change reaches nobody.

  Asymmetric by design, because the two kinds of field have different authority:

  COPY FIELDS  (name, description, subject, content, content_html, variables,
               version)  -> ALWAYS refreshed from the registry.
     The admin surface cannot edit them (UpdateTemplateRequest allows only
     provider_template_id and is_active), so any difference is registry drift,
     never a tenant's choice. `variables` especially MUST track the registry:
     it is the declared order the worker uses to build body_1..N, and drift
     there sends scrambled parameters — the v35 bug in a new disguise.

  provider_template_id -> only FILLED when the tenant's is NULL.
     A non-NULL value is a deliberate remap to the tenant's own MSG91 template,
     which is the whole point of a per-tenant row. Never overwritten; reported
     as provider_conflicts_left_alone.

  is_active -> never touched (a tenant may have switched a message off).
  Nothing is ever deleted. Closed tenants skipped. NULL p_tenant = all tenants.

HOW TO USE IT — the routine after registering a new MSG91 template
  1. Register the template at MSG91.
  2. Wire the GLOBAL registry row:
       update n_jtd_templates set provider_template_id = '<msg91 name>'
        where tenant_id is null and template_key = '<key>';
  3. See what would change (writes nothing):
       select fn_jtd_template_sync(null, true);
  4. Apply:
       select fn_jtd_template_sync(null, false);
  Step 3 is also the "alert" surface — run it any time to see registry drift.
