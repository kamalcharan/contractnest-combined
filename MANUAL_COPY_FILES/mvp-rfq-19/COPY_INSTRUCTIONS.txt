WHAT THIS SOLVES
─────────────────────────────────────────────────
Compliance gap found in conversation: when a coverage item has more than one
unit (e.g. "DG Set ×2") and a FlyBy/catalog service block has a recurring
Service Cycle, "Visits" reads as ambiguous — a reader could assume N visits
means N visits PER unit, when the system actually means N visits covering
ALL units of that coverage group together, per visit. Confirmed by reading
contractEventsDerivationService.ts: quantity is the block's total visit
count, spaced serviceCycleDays apart — it has no concept of "per unit."

Investigated whether a real per-asset audit trail already exists (Sprint 3
scaffolding: EventAssetProgress.tsx / useContractEventAssets /
ContractEventAssetRow) — it does NOT: the UI calls
GET /api/contracts/:id/event-assets, which has no backend route anywhere in
contractnest-api. That's tracked separately now in CLAUDE.md under Future
Review Items ("Sprint 3 — per-asset event proof") for whenever Sprint 3 is
picked up — NOT part of this batch.

Per explicit scope decision ("for now, we will have it UX level"), this
batch is a UX-only fix: make the ambiguity impossible to miss, and give an
escape hatch to split into independent per-unit schedules when that's what
the user actually means. No DB schema change, no new endpoint.

Files Changed:
  - contractnest-ui/src/components/catalog-studio/BlockCardConfigurable.tsx
      Added two optional ConfigurableBlock.config fields: splitUnitIndex,
      splitUnitTotal — marks a block produced by "Split into N independent
      schedules" as already representing exactly ONE unit, so the ambiguity
      banner never re-shows on it.
  - contractnest-ui/src/components/contracts/ContractWizard/steps/serviceBlocksChecklist/ChecklistRow.tsx
      New props: coverageUnitCount (resolved by the caller from the coverage
      group's unit_count), onSplitByUnits (offered on FlyBy rows only). When
      coverageUnitCount > 1 and a Service Cycle is set, both the FlyBy and
      catalog Service Cycle sections now show a one-line disambiguation
      ("N visits cover all M units of X together, per visit — not N visits
      for each unit") plus a "Split into M independent schedules instead"
      action on FlyBy rows.
  - contractnest-ui/src/components/contracts/ContractWizard/steps/ServiceBlocksStep.tsx
      New handleSplitByUnits(blockId): clones a FlyBy block into
      coverageTypes[...].unit_count copies (one per unit, each named
      "<name> — Unit i of N", each keeping the same Visits/Cycle to edit
      independently), removes the original. Wired coverageUnitCount into
      BOTH the catalog and FlyBy ChecklistRow call sites; onSplitByUnits only
      into the FlyBy call site (catalog blocks are reusable master-data
      items — splitting those per-unit is a bigger structural change,
      deliberately deferred, not snuck into this UX-only batch).
  - contractnest-ui/src/pages/contracts/rfq/RfqBuilderPage.tsx
      RFQ's "services" blocks previously had NO link to "coverage" lines at
      all (two fully separate arrays). Added:
        - An "Applies to" dropdown above each FlyBy card in the Scope step
          (only shown when coverage.length > 0) — lets the buyer tie a
          block to a specific coverage line (e.g. "DG Set ×2"), or leave it
          General.
        - setFlybyCoverage / splitFlybyByUnits helpers (same split logic as
          the Contract wizard).
        - coverageUnitCount + onSplitByUnits wired into the RFQ's single
          ChecklistRow call site.
        - The submit() payload now also persists coverageTypeId/
          coverageTypeName inside custom_fields.config (was previously
          computed client-side only and would have been silently dropped on
          submit — same JSONB column already used for flyby_type/
          serviceCycleDays/unlimited, no backend change).

Submodules Affected: contractnest-ui only (no DB migration, no API change)
