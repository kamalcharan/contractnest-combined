THE COMPONENT
  <FileUpload
     target={{ scope: 'contract', contractId, eventId }}   // metered
     target={{ scope: 'tenant', assetKind: 'logo' }}       // not metered
     accept multiple disabled showQuota label hint onUploaded />

  · Quota meter shown BEFORE the work, with 80% / 95% / full states, and the
    dropzone disables itself at full rather than letting someone pick a file
    and then fail. This is the cap design from the spec: a technician learns
    about a problem while they still have options.
  · Real per-file progress from XHR upload events — genuine bytes sent, not a
    spinner that lies. The PUT is the long part on a phone.
  · One bad file in a batch does not abandon the rest.
  · EvidenceChip renders what is already attached, with open + remove.

COMPRESSION
  Images are downscaled to a 1600px longest edge and re-encoded as JPEG (~82%)
  BEFORE the size is declared, so the cap check sees the size that will really
  be stored. A phone photo goes 3–5 MB → ~300 KB, which is what makes 40 MB
  workable and cuts egress by the same factor.

  Every failure path returns the ORIGINAL file instead of throwing. A
  technician must never lose a photo because a canvas call failed on their
  browser — worse compression is acceptable, a lost proof is not. PDFs and
  documents pass through untouched. is_compressed + original_size_bytes are
  recorded on the registry row, so if a per-contract "keep originals" flag
  ever ships we can tell which historical evidence is a reduction.

TOASTS AND LOADERS
  vaniToast throughout — NOT react-hot-toast. The app mounts only VaNiToast,
  so the ~60 files still importing react-hot-toast render nothing (the finding
  recorded in CLAUDE.md on 18 Sep). Loading is the component's own progress
  rows plus a spinner per file; no new loader component was created.
