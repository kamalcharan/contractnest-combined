WHAT CHANGED
------------
The Dues grid's per-cell modal ("Change instalment status") only ever
offered status-correction chips: Adjustment, Waived, Cancelled, Bad
Debt. Those relabel an instalment — they do NOT create a receipt, do
NOT touch amount_settled, and do NOT update the invoice balance. There
was no way, from this screen, to record that a member actually paid
(e.g. in cash) — clicking a cell with an overdue amount gave no path
to settle it as paid.

Added a "Record Payment" button to that same modal, above the status
chips, visible only when the cell has a real open balance. It opens
the EXISTING RecordPaymentDialog component (used on the Contract
Detail page), pre-selecting the specific instalment(s) shown in that
cell so the amount fills in automatically. From there the chair picks
a payment method — Cash, Bank Transfer, UPI, Cheque, Card, Other — an
optional reference/notes, and submits. That creates a real receipt,
settles the event, and updates the invoice balance through the SAME
path already used everywhere else money is recorded in the app — not
a second, parallel write path.

On success the dialog closes and the Dues grid refetches, so the cell
immediately shows the new paid status.


WHY NOT JUST ADD A "PAID" STATUS CHIP INSTEAD
-----------------------------------------------
Considered and rejected. The status chips call a bare PATCH on the
billing event's status field only. Using that to mark something "paid"
would flip the label without creating a receipt or updating
amount_settled/invoice.balance — producing exactly the status-vs-
settled-amount mismatch this codebase already had to fix once
(migration 064, noted in CLAUDE.md). Reusing RecordPaymentDialog avoids
inventing a second settlement path with its own bugs.
