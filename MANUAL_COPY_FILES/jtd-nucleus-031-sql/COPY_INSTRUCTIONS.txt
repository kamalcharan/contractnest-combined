WHAT 031 ADDED
===================================================================

1. admin_delete_tenant(p_tenant_id uuid, p_dry_run boolean DEFAULT true)
   The hard delete, which did not exist. admin_close_tenant_account only
   flips status to 'closed'; admin_reset_all_data only clears the data
   INSIDE a tenant. The t_tenants row was never removable, so the platform
   tenant count never fell.

   28 FK children cascade off t_tenants. 9 more are ON DELETE NO ACTION and
   block the delete, plus a long tail of tenant-scoped tables with no FK at
   all -- 45 tables in total carry a tenant_id. Rather than hand-list them in
   a fragile order, the function sweeps every such table in up to 12 passes
   and lets FK order resolve itself.

   The sweep swallows FK errors per statement -- the exact failure mode fixed
   in 030 -- so it ENDS BY PROVING no row survived and RAISEs if one did,
   instead of trusting the sweep. Refuses the platform admin tenant (is_admin)
   outright. Dry run by default; service_role only.

     select admin_delete_tenant('<uuid>');        -- dry run
     select admin_delete_tenant('<uuid>', false); -- actually delete

   Note: t_tenant_integrations.tenant_id is TEXT, not uuid -- hence the
   ::text comparison in the sweep.

2. admin_purge_orphan_auth_users -- widened from 030.
   The 030 rule required no t_user_profiles row. True of throwaway signups,
   not of a real tenant's users -- so deleting a tenant left its logins
   behind (the first pass after the tenant deletes caught only 3 of 60).
   A profile cascades on auth.users delete, so belonging to no tenant is the
   real test. A platform-admin profile is still never an orphan.
