BATCH: evidence-storage-admin                (Evidence Storage — H)
The admin screen: what is really in the bucket, and what may go
═══════════════════════════════════════════════════════════════════

WHAT THIS IS
───────────────────────────────────────────────────────────────────
The interface you asked for in POA point 3 — "show all folders that
can be deleted, and act as an admin interface for future".

Firebase Storage has no folders. A "folder" is just a shared path
prefix, which is why the Firebase console is such an awkward place to
judge what is safe to remove. This page lists every top-level prefix,
says which model it belongs to, shows WHO depends on it, and lets the
legacy ones go.

  contracts/**   contract evidence   METERED, governed by the registry
  tenants/**     identity assets     unmetered (logos, avatars, icons, QRs)
  tenant_*       LEGACY per-tenant provisioned folders
  anything else  unaccounted for

Only the last two can be deleted here. contracts/ and tenants/ are
refused by the SERVICE, not just hidden in the UI — retiring one of
their files is the registry's job (evidence_mark_deleted) so the sweep
can reclaim it properly.

SUBMODULES AFFECTED: contractnest-api, contractnest-ui
DATABASE: none. No migration in this batch.

⚠️ THE FINDING THAT SHAPED THIS SCREEN
───────────────────────────────────────────────────────────────────
Legacy folders are NOT one per tenant. Live data:

  tenant_c0000000_demo          Trinity Tecnitions, Value Elevators,
                                Freedom Services, Hygene Services   ← 4 TENANTS
  tenant_dd194710_1783503297801 BBB
  tenant_80e3b843_1786802755628 signia
  tenant_70f8eb69_1752782698282 vikuna
  tenant_2ba7d476_1773337307554 stw
  tenant_1f0a8dd2_1781165519722 hubb
  (vikunatechnologies has none)

Deleting "that tenant's folder" in the Firebase console would have
quietly taken four tenants' files. Every row therefore names its
tenants, a shared folder is flagged amber in the list AND again in the
confirm dialog, and the dialog will not enable until the prefix is
typed out in full.

WHAT IT DOES
───────────────────────────────────────────────────────────────────
API
  src/utils/firebaseStorageAdmin.ts        listObjects, listTopLevelPrefixes,
                                           deletePrefix
      listObjects walks EVERY page so count and bytes are true totals even
      when only the first slice is returned — a delete button that
      under-reported what it is about to remove would be worse than useless.
      deletePrefix deletes object by object and counts, rather than the
      one-line bucket.deleteFiles, because this backs a button whose job is
      to say exactly what it did.

  src/services/storageAdminService.ts      NEW. Classification, the
      protected-namespace rule, and the tenant join. Deleting a prefix also
      CLEARS storage_path on every tenant pointing at it — otherwise the old
      pages keep referencing a folder that no longer exists, which is
      exactly how that surface starts throwing.

  src/routes/storageAdminRoutes.ts         GET /overview, GET /browse,
      POST /prefix/delete (confirm must repeat the prefix), plus the
      existing sweep endpoints.

UI
  src/pages/settings/storage-admin/index.tsx    the page, at
      /settings/storage-admin
  src/hooks/queries/useStorageAdminQueries.ts   queries + mutations
  src/App.tsx                                   route
