WHAT IT IS
──────────
  A full-page, one-question-per-screen RFQ builder that follows your sequence
  exactly and stays loose (the buyer gives a FLAVOUR, not a registry record):

    1. What for ...... Equipment / Facility / Service  (Service skips step 4)
    2. Request ....... heading + contract type (nomenclature, prefills term)
    3. Timing ........ start, term, and "last date to apply"
    4. What it covers  pick type + quantity + an OPTIONAL flavour line
                       ("2 DG sets, ~500kVA"). Skipped entirely for a service.
    5. Services ...... flyby lines, each with a cadence (monthly, on-call…)
    6. Vendors ....... your vendor contacts, one or many
    7. Review ........ summary + Send. (Save-as-template shown, disabled —
                       "coming soon", see note below.)

  On send it creates the RFQ and transitions it to 'sent' (the same two calls
  the wizard makes), then shows the request number + CNAK and "sent to N
  vendors". Each vendor still gets their own private link (batch-1 grants).


HOW IT HONOURS "ONLY UX CHANGES"
────────────────────────────────
  Same data, same API, new screens only. It writes:
    * coverage_types + equipment_details  — the flavour (placeholder-flagged,
      added_by_role 'buyer', flavour text in item_name/notes)
    * blocks  — flyby service lines with billing_cycle
    * vendors[]  — {vendor_id, vendor_name, vendor_company, vendor_email}
    * response_deadline, nomenclature_id, start_date, duration
  All of which create_contract_transaction already inserts. Reuses useResources
  (types), useNomenclatureTypes, useContactList (vendors), useContractOperations
  (create + updateStatus). No RfqAssetStep, no shared-wizard changes — the
  contract wizard is untouched.

  Why a flavour, not the registry: the tenant registry is empty platform-wide
  and a buyer describes loosely by nature. Type + quantity + free-text is the
  right level; it lands as placeholder equipment_details, exactly the wizard's
  "add later" model, but purpose-built instead of bent.


REFERENCE-PATTERN NOTE
──────────────────────
  Built clean and self-contained on purpose. The single-column shell (progress
  rail, sticky action bar, one-question screens) is the piece contracts and
  templates will eventually adopt — but only AFTER this proves out in use, so
  we copy from something real rather than a premature abstraction.
