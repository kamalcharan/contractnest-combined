harden-vani-rule-enabled - Migration 025 (already applied live, needs to be committed)

WHY
---
vani_rule_enabled was introduced in migration 022 without the hardening
that every other function in this area uses (SECURITY DEFINER + REVOKE
FROM PUBLIC + GRANT TO service_role). Postgres default granted EXECUTE
to PUBLIC, which was inconsistent with get_vani_rules / update_vani_rule /
start_vani_trial / get_vani_briefing all of which are service_role-only.

Practical impact of the miss was minimal - function is read-only and
returns a boolean - but any authenticated user could enumerate which
notification rules were enabled for any tenant they named. This closes
that inconsistency.

Callers verified safe before revoke:
  - jtd-worker/index.ts:84 uses SUPABASE_SERVICE_ROLE_KEY (grant hit).
  - No other repo callers.
