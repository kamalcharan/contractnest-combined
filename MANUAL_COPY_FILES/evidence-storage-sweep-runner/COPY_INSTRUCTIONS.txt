WHAT THIS COMPLETES
───────────────────────────────────────────────────────────────────
Batch G part 1 (evidence-storage-sweeper) built the database half:
functions that decide WHAT may be reclaimed. Nothing reclaimed
anything, because Postgres cannot delete a Firebase object. This is
the other half.

  storage_cleanup_due()     is a run worth doing at all?
  storage_cleanup_claim()   rows to reclaim, with their object paths
  deleteObject()            the only place bytes actually go
  storage_cleanup_settle()  drop settled rows, KEEP the failed ones
  storage_cleanup_record()  one n_jtd row per tenant per environment

WHY THE API AND NOT THE JTD WORKER
───────────────────────────────────────────────────────────────────
The edge runtime holds no Firebase service account, so the worker
could only ask the API to delete — a hop that buys nothing for a
daily idempotent sweep. And not pg_cron, because the sweep needs
Firebase credentials; putting an API URL and a shared secret in the
database to poke it would be a new secret for no gain.

SAFETY PROPERTIES (each one probed)
───────────────────────────────────────────────────────────────────
  • claim() NEVER returns an 'active' row and settle() refuses to
    remove one. The sweeper can only finish what something else
    already decided was dead.
  • A FAILED delete keeps its row and is retried next run. Dropping
    it would strand the bytes with nothing pointing at them.
  • deleteObject uses ignoreNotFound, so re-deleting is a no-op —
    which is what makes the whole chain safe without a lock.
  • No advisory lock, deliberately (see 004's own comment): it is
    session-scoped and re-entrant, so a pooled connection can leak
    it and block every future sweep. Two sweepers racing duplicate
    work and change nothing else.
  • A failed history row never loses a completed reclaim — the bytes
    are already gone and the rows already settled, so it is reported
    to Sentry rather than thrown.

PRODUCTION CHECKLIST
───────────────────────────────────────────────────────────────────
  Transaction Management : each RPC is its own transaction; the
                           sequence is idempotent by design rather
                           than atomic (it spans an external API)
  Race Conditions        : in-process `running` guard; cross-process
                           safe by idempotency, no lock (see above)
  Error Handling         : every step checked; failures retried next
                           run; captureException throughout; a
                           skipped sweep reports why
  Toasts / Loaders       : N/A — no UI in this batch (batch H)
