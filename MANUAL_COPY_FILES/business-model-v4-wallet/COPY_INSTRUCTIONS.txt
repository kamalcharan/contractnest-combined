THE DESIGN CHANGED MID-STREAM - READ THIS FIRST
-------------------------------------------------------------------
024_wallet_mode.sql was the FIRST version: a bespoke topup_wallet()
RPC, its own payment trigger, meant to be fronted by a brand new API
route + UI screen. Owner correction after seeing that plan: "why
API? it already part of contract/template" / "we have to reuse
rather building bulk of code repeatedly". A wallet top-up is
structurally just another thing a tenant buys from the platform -
exactly what Phase D's credit-pack pipe already does (purchase_
topup_template -> t_contracts -> invoice -> pay -> fn_apply_topup_
grants). So 025_wallet_via_pack_purchase.sql RETIRES the bespoke RPC
and teaches the EXISTING pack pipe a second template category
instead. Net result: no new API route, no new UI screen - wallet
top-ups reuse the "Credit packs" section already on the Plans page,
now relabeled "Credit packs & wallet top-ups".

Both files are needed, in order, on a fresh environment:
  1. 024_wallet_mode.sql   - creates trg_fn_wallet_charge (the hard-
     block per-creation deduction trigger - this part was NEVER
     retired, it's the one genuinely new piece of infrastructure)
     and fixes a pre-existing bug in trg_fn_context_credit_flags.
     Its OTHER pieces (topup_wallet, fn_apply_wallet_topup, the
     payment trigger, and its edits to get_tenant_context /
     trg_fn_plan_contract_lapsed) are all superseded by step 2.
  2. 025_wallet_via_pack_purchase.sql - drops the three superseded
     024 objects, extends purchase_topup_template + fn_apply_topup_
     grants to handle a 'wallet_topup' category template, and
     reverts the get_tenant_context / trg_fn_plan_contract_lapsed
     edits back to their simpler original form (both packs AND
     wallet top-ups now share metadata.source='topup_purchase', so
     the "exclude a purchase contract from plan resolution" check
     only ever needed one condition, not two).
Do NOT skip file 1 - trg_fn_wallet_charge (the actual money-deducting
trigger) only exists there, and 025 does not recreate it.

-------------------------------------------------------------------
WHAT billing_mode ACTUALLY IS
-------------------------------------------------------------------
The column value is 'per_contract' - matches the existing CHECK
constraint chk_tenant_context_billing_mode
(freemium / poc / per_contract / plan / exempt). Internal naming
(wallet_balance_paise, credit_type='wallet' in the journal,
'wallet_topup' as the template category) stays "wallet" throughout -
that's what this actually is in plain English - only the
billing_mode COLUMN VALUE has to match the constraint's spelling.

-------------------------------------------------------------------
THE THREE RULES, AS BUILT
-------------------------------------------------------------------
  ₹200 per contract, ₹400 per RFQ - deducted from wallet_balance_paise
    the MOMENT the row is created (BEFORE INSERT trigger, trg_fn_
    wallet_charge, from 024, untouched by 025)
  Hard block on insufficient balance - the INSERT itself fails with
    an exception, nothing is created. Owner decision 2026-08-09,
    explicitly different from the soft/never-block posture Free/
    Quarterly/Yearly have (D3) - running out of money to pay for a
    contract is treated differently from running out of a plan's
    included allowance.
  15 WhatsApp + 15 Email credits granted per creation - reuses the
    metering machinery that already exists (trg_fn_contract_
    consumption, unchanged); credit_grant_rates gets set on the
    tenant's context the same way a plan subscription sets it,
    now done inside fn_apply_topup_grants's new wallet branch
    instead of a bespoke function.
  Minimum top-up - now whatever price the wallet_topup TEMPLATE is
    authored with in catalog-studio (same as a credit pack's price),
    not a hardcoded RPC parameter. The ₹1,000-minimum rule from the
    original spec is enforced by whoever authors the template
    (don't publish a wallet_topup template priced below ₹1,000) -
    there's no code-level floor anymore because there's no longer a
    free-form "top up by any amount" entry point at all. This is a
    deliberate consequence of the reuse decision: wallet top-ups are
    now fixed-denomination products, exactly like credit packs,
    not an arbitrary-amount wallet feature.

-------------------------------------------------------------------
DELIBERATELY NOT BUILT: 1-YEAR EXPIRY
-------------------------------------------------------------------
BUSINESS_MODEL_V3_SPEC.md Section 5.1 calls the proper FIFO top-up-lot
expiry system "the largest single piece of work the commercial model
implies" - a real lots ledger, oldest-first consumption, a per-lot
expiry job. Owner decision 2026-08-09: ship without expiry first, same
posture notification credits already have (D2 - nothing expires).
wallet_balance_paise is a single running balance; top-ups only add to
it, nothing ever removes value except spend. Revisit as its own piece
of work if/when expiry is wanted.

TWO REAL PRE-EXISTING BUGS FOUND WHILE TESTING (both fixed)
-------------------------------------------------------------------
1. billing_mode value mismatch (topup_wallet, 024, now moot since
   that function is retired, but worth knowing the pattern exists):
   the first live test used billing_mode='wallet' and hit
   chk_tenant_context_billing_mode's CHECK violation - the constraint
   has only ever allowed freemium/poc/per_contract/plan/exempt.
   Fixed by using 'per_contract' as the real column value everywhere,
   keeping "wallet" only as internal/readable naming (column names,
   function names, journal credit_type, template category).

2. trg_fn_context_credit_flags (built in Phase A, months before this
   session) computed "is this tenant active enough to send
   notifications" from a hardcoded list of billing_mode values that
   included 'wallet' - a value that was NEVER valid (see bug 1). This
   function is untouched by the 025 rework, so the fix from 024 still
   stands. Because per_contract/wallet mode had never been exercised
   by any real tenant before this session, this was completely
   silent: the credit-grant call failed a NOT NULL constraint, caught
   by the caller's blanket exception handler, logged only as a RAISE
   WARNING nobody was watching. Caught by testing a real charge event
   live: usage_contracts and the 15/15 credit grant were both
   stubbornly zero after a contract creation that should have moved
   both. Traced to this one line, fixed, retested - confirmed working.

   This means per-contract/wallet billing_mode has been silently
   broken since Phase A, on a codepath nothing had ever exercised. A
   repo-wide grep for the string 'wallet' against billing_mode
   comparisons would catch any other latent copies of this mistake.

PRODUCTION CHECKLIST
-------------------------------------------------------------------
  Transaction management : yes - purchase_topup_template runs inside
                           its own transaction (contract + invoice
                           creation atomic); the deduction in
                           trg_fn_wallet_charge runs BEFORE INSERT,
                           inside the same transaction as the
                           contract/RFQ creation itself, so a charge
                           and its record commit or roll back together
  Race conditions        : yes - trg_fn_wallet_charge takes
                           FOR UPDATE on the tenant context row before
                           checking balance, so two concurrent
                           contract creates cannot both pass the
                           balance check against the same money;
                           fn_apply_topup_grants's wallet branch also
                           takes FOR UPDATE before adding a top-up
  Error handling          : yes - hard block via RAISE EXCEPTION is
                           the intended behavior here (owner decision,
                           different from the soft plans); purchase_
                           topup_template and fn_apply_topup_grants
                           each return a JSON error rather than a
                           bare 500 on failure
  Idempotency             : yes - fn_apply_topup_grants's existing
                           reference_type/reference_id EXISTS guard
                           (built in Phase D for credit packs) covers
                           the wallet branch too, tested live (round
                           2, step 4 above) with a real double-payment
                           simulation
  Toasts / Loaders        : yes - reuses the exact same purchasePack
                           mutation, toast, and loading-state wiring
                           the Plans page already has for credit
                           packs (handleBuyPack et al.) - nothing new
