WHAT THIS IS
  The broker. Firebase becomes a dumb blob store; every byte in or out goes
  through the API with the Admin SDK and a short-TTL signed URL, authorised in
  Postgres by contract_membership() before a URL is minted.

  Nothing in the running product uses it yet — the existing upload paths are
  untouched. Batch D migrates the five live call sites onto it.

HOW AN UPLOAD WORKS
  1. Client asks for a slot, declaring file name, mime and size.
  2. RPC checks membership (WRITE is contract-creator only), the mime allowlist
     and the cap — all BEFORE the client does the work, so a technician learns
     about a full quota before the visit, not after.
  3. API mints a 10-minute signed PUT url; a pending registry row exists.
  4. Client PUTs the bytes straight to Firebase.
  5. Client confirms; the API reads the object back and records its TRUE size.
     A declared size is a client claim — only the read-back size is metered.
  An unconfirmed slot leaves an orphan the sweeper reclaims (batch G).

THE CAP, AS SPECIFIED
  Refused only once usage has ALREADY reached quota, so a tenant under the line
  always finishes the upload in hand and is then locked until they top up —
  a field emergency becomes an office task. warn_level: ok / warning (80%) /
  critical (95%) / full.

CNAK — closed the gap found in batch A
  t_contract_access already had expires_at and is_active, and
  validate_contract_access already enforced both — but nothing ever SET an
  expiry, so all 159 live grants were indefinite bearer tokens.
    · expires_at now DEFAULTS to 90 days on new grants
    · a successful CNAK read pushes the expiry out 90 days (an active
      relationship never expires; an abandoned link does)
    · a grant with NULL expiry stays permanent — never given one retroactively
    · revoke_contract_access() turns one off; creator only
  ⚠️ The 159 EXISTING grants were deliberately left NULL. Expiring live
     contract-review links retroactively would break links already in flight.
     Backfilling them is a separate owner decision.

⚠️ DO NOT DEPLOY firebase/storage.rules YET
  The API still uploads through the Firebase CLIENT SDK with signInAnonymously()
  in three places (storageService, tenantProfileService, integrationService).
  Those ARE subject to storage rules. Deploying deny-all before batch D migrates
  them would break avatar, logo, block-icon and QR uploads immediately.
  Deploy it at the END of batch D, then verify a client-SDK read fails from a
  test harness while an API-minted signed URL still works.
