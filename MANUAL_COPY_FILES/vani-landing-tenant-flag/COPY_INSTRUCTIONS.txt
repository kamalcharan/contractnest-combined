BATCH: vani-landing-tenant-flag (2026-09-16) — stitches 3 + 4:
       VaNi landing + entitlement service read the tenant truth
═══════════════════════════════════════════════════
Follows vani-tenant-flag (step 1) and vani-automation-rules (step 2).

What changes for a user:
  · /vani/landing: the badge and both CTAs now come from
    flags.vani_enabled (tenant-context API). "VaNi is on" / "VaNi is on ·
    trial, N days left" / "VaNi is off · 1-week free trial" / "VaNi is off ·
    trial ended". Starting the trial still calls start_vani_trial, which
    sets t_tenants.vani_enabled (step 1) — and now the landing, Automation
    Rules and Briefing all refetch immediately.
  · /vani/briefing: gated on flags.vani_enabled.
  · API: vaniEntitlementService reads vani_is_enabled() — the SAME function
    get_tenant_context emits — so /api/vani/entitlement, the Briefing 403
    gate and the VaNi COMPOSER gate (/api/vani/composer/*) all follow the
    tenant flag. VANI_ENTITLEMENT_MODE is REMOVED (it was the second switch).

⚠️ BEHAVIOUR CHANGE ON DEPLOY (this is the business model, stated so it is
   not a surprise): production ran in VANI_ENTITLEMENT_MODE=open — every
   tenant was "entitled". After this API deploys, only tenants with the
   tenant flag are: today BBB, signia and vikuna (admin). For everyone else
   the Briefing shows its locked panel, and the LLM composer entry points
   (contracts hub, create-contract, catalog templates — they call
   /api/vani/composer/entitlement) hide. No automation behaviour changes —
   engines are still ungated (stitch 6).
   To enable another tenant by hand:
     update t_tenants set vani_enabled=true, vani_enabled_until=null,
            vani_enabled_source='admin' where id='<tenant>';

Submodules affected: contractnest-ui, contractnest-api. No DB change.
