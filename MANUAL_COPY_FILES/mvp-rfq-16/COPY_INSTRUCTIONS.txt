WHAT CHANGED
────────────────────────────────────────────────────────────
The flyBy Service Cycle redesign shipped in mvp-rfq-15 had 2 of the 4 fields
catalog-studio's "Delivery Settings → Cycle Configuration" defines (Cycle
Period, Repeat on a fixed weekday). This batch adds the other 2, in the same
order/copy as the source:

  3. First occurrence date (optional) — date picker. "Set this when the real
     first visit doesn't match the computed date — overrides the weekday
     anchor above for the first occurrence only." Persists to
     config.serviceCycles.anchorDate.
  4. Grace period — number + "days — buffer before marking overdue".
     Persists to config.serviceCycles.gracePeriod.

Both live in the SAME config.serviceCycles cluster as the existing
days/anchorWeekday fields (co-located, matching how ChecklistRow already reads
anchorWeekday from there). The "Next occurrences" preview now honors an
explicit First occurrence date as the starting point when set.

────────────────────────────────────────────────────────────
PERSISTENCE — confirmed wired to API/DB, verified against the actual RPC
────────────────────────────────────────────────────────────
Checked supabase/migrations/contracts/041_rpc_equipment_details_support.sql:
create_contract_transaction stores `custom_fields` VERBATIM —
COALESCE(v_block->'custom_fields', '{}'::JSONB) — and returns it the same way
on get_contract_by_id. RfqBuilderPage.tsx's payload already does
`config: { ...(b.config || {}), ... }`, which spreads the full serviceCycles
object (days/anchorWeekday/anchorDate/gracePeriod) through automatically.
So these two new fields persist through the SAME already-proven path —
NO backend/API/migration change was needed, and none was made.
