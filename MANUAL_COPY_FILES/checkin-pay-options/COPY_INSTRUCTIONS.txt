═══════════════════════════════════════════════════
Built on current main (ui a5a2e78 · api 552c285 · edge aff2930), i.e. after
payment-request-framework was merged. Independent of home-create-options and
session-timeout (no shared files) — copy order with those does not matter.

Owner decisions: pay first, then check in (as today); desk QR first; show
"Pay to UPI ID" (not hidden); generic for every tenant — online payment
appears whenever the tenant has a payment gateway in that environment.

WHAT IS REUSED (nothing parallel was built)
  · Razorpay: the existing payment-gateway edge function, PaymentGatewayService,
    create_payment_request, verify_gateway_payment, the payment webhook, and
    the existing useRazorpayCheckout hook (one optional `verify` option added
    so a no-login page can verify through its own route).
  · Instalment settlement: the existing record_invoice_payment_with_allocations
    (what the chair's confirm already uses). Same invoice rule as the chair's
    confirm (gs_confirm_declaration).
  · UPI: the shared OfflineUpiPay card + utils/payments/upi.ts (same card as
    the contract pay page). Added an optional `layout="in_person"`; the pay
    page and onboarding preview are unchanged.
  · Duplicate checks, "already recorded today", "Did you pay?" gate, come-back
    nudge, leave-for-UPI-app sheet: unchanged, now wired to the shared card.

NEW, AND WHY IT IS NEEDED
  The existing public pay routes are keyed to a contract review link
  (CNAK + secret). Check-in only has the meeting QR token, so two token-
  scoped routes bind the same gateway flow to the token:
    POST /api/checkin/:token/pay/order   { member_id, billing_event_id }
    POST /api/checkin/:token/pay/verify  { request_id, gateway_* }
  The tenant always comes from the token on the server, never the client.

DB — migration business-model-v2/046_checkin_online_payment.sql
  ⚠ ALREADY APPLIED LIVE (2026-10-08). Do NOT re-run. Source of record only.
  · gs_checkin_payment_config + `online`
  · gs_checkin_gateway_order / _attach / _request (token-gated)
  · fn_payment_request_allocations — a request's instalment, only while it
    still has room (locks the instalment; a second payment for the same
    instalment is recorded on the invoice without an allocation, never lost)
  · verify_gateway_payment + process_payment_webhook now record through
    record_invoice_payment_with_allocations. Requests without an allocation
    (every contract pay-page payment) get [] and behave exactly as before.
  Probed in a rolled-back transaction on a BBB Test member (CN-1026, ₹4,500):
    order ok · bad-debt instalment refused · other member refused · attach ok ·
    verify → receipt RCP, instalment 4500/4500 paid, invoice 36,000 → 31,500 ·
    second order for same instalment → no allocation · order after paid →
    already_paid.
