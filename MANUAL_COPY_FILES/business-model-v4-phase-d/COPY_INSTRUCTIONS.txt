A REAL BUG CAUGHT AND FIXED WHILE BUILDING THIS
-------------------------------------------------------------------
handleGetPlanTemplates (the /plans listing) has never filtered on
category. Real plans are tagged category='service_delivery'; nothing
enforces that. Once a pack template is published (is_public=true,
same gate a plan uses), it would have started appearing as a PLAN
CARD on /businessmodel/tenants/pricing-plans - no limits, its
one_time grant mislabeled as "credits each time you create a
contract or RFQ". Caught this live during testing: flipped the test
pack's is_public to TRUE, and it appeared in a raw run of the plans
query with no category filter.

Fixed by excluding category='topup_pack' from the /plans query.
Plans themselves are not required to carry any particular category -
only packs are excluded, which is the one thing that must never
render as a plan.

-------------------------------------------------------------------
TESTED LIVE, END TO END, THEN CLEANED UP
-------------------------------------------------------------------
Built a disposable test tenant (not Trinity, not CN-1001 - a throwaway
so nothing real was touched), and ran the actual chain against the
test pack (386ab8ce, "WhatsApp 500 Pack", Rs.1500 -> 500 WhatsApp
credits):

  1. purchase_topup_template -> contract CN-1002 raised, credits_pending: true
  2. invoice INV-10002, Rs.1500.00, unpaid - same shape as a plan's invoice
  3. subscribe_tenant_to_plan on the SAME test tenant, for the real Free
     plan -> succeeded (CN-1003). Confirms the topup contract does NOT
     trip ALREADY_SUBSCRIBED.
  4. get_tenant_context on that tenant -> subscription resolved to CN-1003
     (Free), not CN-1002 (the pack). credits.whatsapp still 0 - correctly
     pending, nothing granted yet.
  5. Flipped INV-10002 to paid -> credits_whatsapp jumped 0 -> 500.
     Journal row: transaction_type=topup, reference_type=topup_contract,
     reference_id=<the pack's contract id>, balance_before=0,
     balance_after=500.
  6. Flipped the SAME invoice unpaid -> paid again (simulating a duplicate
     webhook) -> still exactly 1 journal row, still 500 credits. The
     unique partial index held.
  7. Deleted every row this created (journal, context, invoice, contract
     blocks/events, both contracts, the contact, the tenant, an
     auto-seeded t_vani_rules row) and restored the test pack template to
     is_public=false. Verified zero rows remain across all seven tables.

Also fixed, permanently, on the live template: its category was
'plan' (a leftover from before packs had their own tag) - corrected
to 'topup_pack'. is_public is back to FALSE, same as before this
session - it still cannot appear for sale.
