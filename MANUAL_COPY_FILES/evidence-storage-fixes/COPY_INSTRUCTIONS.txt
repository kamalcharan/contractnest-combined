1. contractnest-api/tsconfig.json — tsc now actually runs
───────────────────────────────────────────────────────────────────
Added "ignoreDeprecations": "6.0".

WHAT WAS WRONG: moduleResolution "node" and baseUrl are deprecated in
TS7, so tsc emitted TS5107/TS5101 and ABORTED BEFORE COMPILING ANY
FILE. `npx tsc --noEmit` reported 2 errors and exited 0 having checked
nothing. Type errors only surfaced when ts-node compiled at runtime
and crashed the dev server — which is exactly how the [2305, 2305]
crash reached you instead of me.

⚠️ RUN IT ONCE AFTER COPYING:
      cd contractnest-api
      npm install
      npx tsc --noEmit
   This is the first honest typecheck the API has had. Expect
   pre-existing errors that have been invisible; none are from this
   work. The number it prints is your new baseline.
   (I cannot give you that number — node_modules is empty in my
   container, so what I measure is dominated by "Cannot find module
   'express'".)

   Proper fix later: moduleResolution "bundler" or "node16", drop
   baseUrl for relative paths, remove this flag.

2. contractnest-ui/src/App.tsx — 347 silent toasts speak again
───────────────────────────────────────────────────────────────────
react-hot-toast's <Toaster> was commented out when vaniToast replaced
it, but 68 files and 347 call sites still use it — so every one of
them rendered NOTHING. Worst hit: OnboardingLayout (22 calls),
useGroupSessionsDashboard (18), BBBProfileOnboardingPage (13),
AvatarSection (11). A new tenant hitting an onboarding error saw no
message at all.

BOTH systems are now mounted: vaniToast top-right (the standard),
react-hot-toast bottom-right. That is a STOP-GAP, said so in the
code. The real fix is migrating those 68 files to vaniToast as each
is touched; the line goes when the last one does.

  You will now see two visual toast styles until that migration is
  done. That is the trade for not losing 347 error messages.

3. PersonalInfoSection.tsx — unsaved-changes warning actually fires
───────────────────────────────────────────────────────────────────
The page passes onChangeDetected={setHasUnsavedChanges}. The prop was
DECLARED and never called, so hasUnsavedChanges stayed false forever
and this guard was dead:

    if (hasUnsavedChanges) {
      if (!confirm('You have unsaved changes...')) return;
    }

Edit your profile, press Back, lose the edit with no warning.

Now reported from a comparison against the loaded profile, not a
has-typed-anything flag: typing a change and undoing it does not
leave a false warning, and saving or cancelling resets the baseline
so the warning clears.

4. services/api.ts + services/maintenanceService.ts
   — one 503 no longer bricks the session
───────────────────────────────────────────────────────────────────
TWO separate faults that combined into a trap:

  (a) ANY 503 from ANY endpoint declared platform-wide maintenance.
      503 is a generic status — a crashed edge function, a gateway
      hiccup, a rate limiter, one route reporting a missing config.
      Maintenance is declared by the x-maintenance-mode header, which
      the success path already honoured; the error path ignored it.

  (b) The flag was cached FOREVER. checkMaintenanceStatus() returned
      the stored value first and unconditionally. Nothing ever wrote
      false, nothing removed it, and clearMaintenanceInfo() existed
      but was called by NOTHING.

Together: one unrelated 503 put the session behind the maintenance
page permanently, surviving reload, and the only escape was
sessionStorage.removeItem('maintenance_info') in the console. This is
exactly what happened when /api/evidence/slot returned 503 for a
missing Firebase config — the maintenance page persisted even after
the env vars were removed.

FIXED:
  • A 503 without x-maintenance-mode is now an ordinary error, logged
    with the endpoint that produced it, and nothing is cached.
  • Any successful response clears the flag — proof the platform is
    serving.
  • Cached verdicts carry storedAt and expire after 60s; stale,
    malformed, or pre-fix values are discarded so the API answers.
  • An unreachable API or a malformed payload is NOT maintenance.
    Showing the app and letting calls fail beats locking the user out
    over a network blip.

⚠️ COPY ORDER — App.tsx and PersonalInfoSection.tsx are also carried
by evidence-storage-cleanup and evidence-storage-migrate. All copies
are byte-identical, so any order is fine.
