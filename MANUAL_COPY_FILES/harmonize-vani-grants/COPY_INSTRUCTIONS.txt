harmonize-vani-grants - Migration 026 (already applied live)

WHY THIS IS THE REAL FIX
------------------------
The Railway "Automation rules could not be loaded" error was caused by
a pre-existing deviation in the vani_* function grants, NOT the code
we wrote today, and NOT a missing env var on Railway.

The codebase convention for RPC grants is:
  GRANT EXECUTE ON FUNCTION ... TO PUBLIC, anon, authenticated, service_role

Every other RPC the API calls follows this pattern (get_tenant_cadence_settings,
upsert_tenant_cadence_settings, materialize_tenant_resources, icp_similar_tenants,
insert_audit_logs_batch, seed_sample_contacts, and dozens more). Safety
is enforced by SECURITY DEFINER + explicit p_tenant_id parameter inside
the function body, not at the grant boundary.

The four pre-existing vani_* functions were the outliers - granted only
to postgres + service_role. This worked in dev (where SUPABASE_SERVICE_ROLE_KEY
env var was set, masking the deviation for a year) but failed on Railway
(which only has SUPABASE_KEY = anon, matching every other API service).

I compounded the deviation earlier today in migration 025 by "hardening"
vani_rule_enabled to the same wrong precedent instead of the codebase's
actual convention. This migration undoes 025 and brings all five vani_*
functions in line.

Applied live 2026-08-01. Verified all five now grant to
PUBLIC + anon + authenticated + postgres + service_role.
