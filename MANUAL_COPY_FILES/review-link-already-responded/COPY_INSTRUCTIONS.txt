─── WHAT WAS WRONG ──────────────────────────────────
 1. The registered MSG91 WhatsApp button URL is
    https://www.contractnest.com/contract-review{{1}} — no '?'. The code
    sent the suffix as "cnak=…&secret=…" (its comment assumed the template
    carried the '?'), so the phone opened /contract-reviewcnak=… — no such
    route → the SPA's 404 page. WhatsApp then appended ?fbclid=… to what it
    took for a query-less URL.
 2. Independently: opening a valid link after the buyer accepted returned
    {valid:false, error:"This contract has already been accepted"} and the
    page rendered a red "Access Error" card.

─── WHAT CHANGED ────────────────────────────────────
 contractnest-edge/supabase/functions/contracts/jtd-integration.ts  (DEPLOYED)
 · WhatsApp suffix now carries the '?' itself: ?cnak=…&secret=…
   Byte-identical to the deployed bundle otherwise (only this file
   differed, and only in comment dashes).
 contractnest-ui/src/pages/contracts/review/ReviewLinkRedirect.tsx  (new)
 contractnest-ui/src/App.tsx
 · Catch-all route: a path starting with /contract-review<junk> is
   normalised to /contract-review?<junk> (leading '?'/'/' stripped) before
   the 404 page — so links from the OLD template shape still open, and if
   the MSG91 template is ever edited to include '?', the resulting
   "??cnak=" also opens.
 contractnest-ui/src/pages/contracts/review/index.tsx
 · Param reader accepts "?cnak" keys and cuts a trailing "?fbclid=…" off
   the secret.
 · New state card when the RPC says already_responded: green "Already
   accepted" (date, contract, seller; "Add to my ContractHub" →
   /contracts/claim?cnak&secret when not yet claimed, "log in to open it"
   when claimed) · amber "This link has expired" · red "Contract declined".
   "Access Error" remains only for genuinely invalid links.
 contractnest-edge/.../contracts/080_validate_access_already_responded.sql  (LIVE)

   returns valid:false + already_responded, status, responded_at, claimed,
