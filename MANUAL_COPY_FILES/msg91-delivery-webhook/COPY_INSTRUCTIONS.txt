WHAT THIS SOLVES
─────────────────────────────────────────────────
Nothing ever moved an n_jtd row past status='sent'. 'sent' only means MSG91
accepted the request and returned a request_id — it says nothing about whether
WhatsApp delivered the message. That blind spot let attendance_ack and
payment_thankyou fail silently from 1–4 Aug 2026: every row read 'sent', every
message was rejected by WhatsApp on delivery with "Parameter name is missing or
empty". It surfaced only because a human checked a handset.

═══════════════════════════════════════════════════
🔌 MSG91 NEEDS NO CHANGE — reports already flow
═══════════════════════════════════════════════════
MSG91 already has a WhatsApp webhook registered:

    Name    BBB
    Event   On Inbound Report Received     ← these ARE the delivery reports
    URL     https://n8n.srv1096269.hstgr.cloud/webhook/whatsapp-msg91

So MSG91 has been sending delivery reports all along — to n8n, not to us.
That is the whole reason n_jtd never updated. (The second webhook, VaNi /
"On Inbound Request Received", is inbound replies from members — a different
event, leave it alone.)

RECOMMENDED WIRING — forward from n8n, change nothing in MSG91:

  In the n8n workflow behind /webhook/whatsapp-msg91, add an HTTP Request node
  alongside whatever it already does:

      Method  POST
      URL     https://uwyqhzotluikawcboldr.supabase.co/functions/v1/msg91-webhook
      Body    the incoming webhook payload, passed through unchanged
      Headers Content-Type: application/json

  MSG91 config untouched, n8n keeps doing its existing job, and ContractNest
  starts seeing delivery status.

ALTERNATIVE (not recommended): repoint the MSG91 URL straight at the endpoint.
Simpler, but whatever the n8n workflow currently does with these reports stops
happening. Only do this if that workflow is dead.

OPTIONAL HARDENING: set edge env var MSG91_WEBHOOK_SECRET to any random string,
then append ?token=<that string> to the forwarding URL. While unset the
endpoint accepts unauthenticated callbacks and logs a warning on each — chosen
so it works the moment it is deployed. Blast radius is small either way: it can
only advance the status of rows that already exist.

🔎 GET THE REAL PAYLOAD FROM n8n
═══════════════════════════════════════════════════
n8n has been receiving genuine MSG91 delivery reports for weeks. Its execution
history therefore contains exactly the payload shape this endpoint has had to
guess at. Open any recent execution of the whatsapp-msg91 workflow, copy one
report body, and the extraction can be tightened from "walk the JSON looking
for anything id-shaped and status-shaped" to exact paths.

The endpoint works either way — this is a refinement, not a fix.

Production Checklist:
  ✅ Transaction Management: single-row updates, no multi-statement work to
     roll back. Each event applied independently.
  ✅ Race Condition Handling: statuses are RANKED and only ever move forward
     (created<pending<queued<processing<sent<delivered<read), so out-of-order
     callbacks — a late 'delivered' arriving after 'read' — cannot walk a row
     backwards. 'failed' is terminal and always recorded.
  ✅ Error Handling: always returns HTTP 200, including on unparseable bodies,
     so a provider retry storm can never be triggered; falls back to
     form-encoded parsing if the body is not JSON; unmatched provider ids are
     logged rather than treated as errors (callbacks for messages sent by
     other systems are expected); recursion depth capped at 8.
  ✅ Toasts: N/A — server-side endpoint, no UI.
  ✅ Loaders: N/A — server-side endpoint, no UI.

📌 WHY THIS MATTERS
═══════════════════════════════════════════════════
Once wired, "did it actually arrive" becomes a query instead of a phone check.
Any future template or parameter-style breakage shows up as rows stuck at
'sent' or flipping to 'failed', within minutes, instead of going unnoticed for
days.
