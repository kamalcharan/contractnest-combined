PRODUCTION CHECKLIST
-------------------------------------------------------------------
  Transaction management : yes - reserve/charge/release are single RPCs,
                           each atomic; the row lock is taken inside
                           fn_credit_state
  Race conditions        : yes - reservation (FOR UPDATE on the context
                           row) stops two workers spending the same last
                           credit; a unique partial index on
                           t_credit_journal makes double-charging
                           impossible even under a retry racing itself
  Error handling         : yes - every credit path fails OPEN. A metering
                           outage never blocks a message and never
                           rewrites a sent message as failed

  Loaders                : existing - the page's Loader2 spinner; the

DESIGN DECISIONS WORTH KNOWING
-------------------------------------------------------------------
NOT CHARGED, deliberately:
  - user_invite, user_created, contract_signoff. These are already
    exempt from the TEST-env guardrail, the channel kill switch and the
    per-message-type toggle, for the same reason: a tenant who cannot
    invite a teammate or let a counterparty reach the signing page has
    an outage, not a saving.
  - is_live = false. Test-env email and WhatsApp are already blocked
    from real delivery; charging for a send that never happens would be
    theft.
  - billing_mode 'exempt' (the platform tenant), and any tenant with no
    context row at all. BBB has no context row, so BBB is untouched by
    all of this.

POOL ORDER: the channel's own pool first, the shared pooled bucket as
fallback. The chosen pool is written to n_jtd.metadata.credit so a retry
spends from the same place it reserved from.

PARKED IS NOT FAILED: a JTD in 'no_credits' keeps its place in a FIFO
queue, is not retried, is not sent to the DLQ, and releases itself the
moment credits arrive. The UI says "waiting", never "failed" - the
difference between a tenant who tops up and one who thinks they must
re-send everything.
